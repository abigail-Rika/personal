# 产品经理就是 Context Engineer

> 组内分享 · 30 分钟

---

## 开场：一个发现（3 分钟）

最近用 AI 干活，有个发现越来越强烈：给 AI 提需求和给研发提需求，踩的坑是一模一样的。

- 需求写模糊了 → 研发做出来不对 → 返工
- Context 给不够 → AI 输出离谱 → 重来

但 AI 比研发"诚实"——它不会脑补你没说的东西，不会假装听懂了，缺什么就缺什么，反馈还是秒级的。

所以我现在觉得，PM 的核心能力不是"写 PRD"，是"构建 context"——让对方在正确的信息环境下做出正确的事，不管对方是人还是 AI。

把 PM 日常工作拆开看，全是 context building：

| 你在做什么 | 本质是什么 |
|---|---|
| 写 PRD | 给研发构建 context——做什么、为什么、边界在哪 |
| 需求评审 | 验证 context 是否被正确接收 |
| 写验收标准 | context 的压缩——用最少信息定义"什么算对" |
| 给老板汇报 | context 的分层——大量细节压缩成几个关键判断 |
| 跨团队对齐 | context 的翻译——让不同背景的人看到同一张图 |

PM 不生产功能。PM 生产 context。功能是研发生产的，他们做对了，是因为你给了足够好的 context。

这不只是个人体感。2025 年下半年，Manus、Anthropic、OpenAI 三家先后发布了 Agent 落地经验的技术文章，核心关键词都是同一个——**Context Engineering**。Anthropic 的原话是："Building with language models is becoming less about finding the right words, and more about 'what configuration of context is most likely to generate our model's desired behavior?'"

AI 时代把这件事放大了：你 context 能力多强，你能撬动的产出就多大。

## 我踩过的三个阶段（5 分钟）

### 阶段一：裸聊

刚开始用 AI 就是直接在对话框打字。每次都要铺垫半天背景。每次对话都在重复构建相同的 context。

### 阶段二：写 Rules

Cursor 有个机制——可以在 `.cursor/rules/` 目录下放配置文件，AI 每次启动都会读。

我写了这些：
- **协作协议**——怎么跟我配合（先理解现状再动手、不擅自降级、有疑问先问）
- **产品上下文**——我们的产品是什么、业务架构、核心指标
- **UI 规范**——颜色体系、字重、圆角、组件规则
- **交互原则**——23 条产品专属规则
- **增长业务上下文**——流量分级定义、渠道评估、投放链路、转化漏斗
- **增长实验规范**——AB 测试怎么设计、实验结果怎么评估

效果立竿见影。AI 不再每次从"你们产品是做什么的"开始，它打开对话就知道自己在哪家公司、该遵守什么规矩。

但问题来了。

### Rules 解决不了的事

Rules 装的是"不变的规则"——产品背景不会天天变，UI 规范也稳定。

可有一类知识不是写一次就完的。它在协作中长出来：

- PRD 写了三版才过——问题出在哪？
- AI 理解错了一个业务概念——gap 在哪？
- 第一次接通某个工具——关键步骤是什么？
- 做流量承接分析，发现"析出量大 ≠ 析出质量高"——这个反直觉的发现怎么留下来？
- 用增长 PRD 规范做对照评审，发现"一句话假设"和"用户视角描述"最容易漏——下次怎么不漏？

这些经验性知识，Rules 装不下。对话结束就丢了。下次遇到同样的问题，AI 还会犯同样的错。

就像一个永远在入职第一天的新人——每天早上都从"你好我是 XX"开始。能力不差，但没有积累。

### 阶段三：搭知识体系

受 stonepage 的《Agent 知识工程实践》启发，里面有句话说得很准：

> Prompt Engineering 优化的是单次对话的表达效率，Knowledge Engineering 解决的是 agent 的认知基础。前者是战术，后者是战略。

换句话说——**agent 不是菜，他只是不知道。**

于是我搭了一套知识沉淀的东西。说起来也不复杂，就是文件夹 + Markdown，全文搜索就能找。

## 知识体系长什么样（12 分钟）

> 这是今天的重点。

### 两层架构

```
第一层：Cursor Rules（不变的规则）
├── 协作协议          ← 常驻，每次对话都在
├── 产品上下文        ← AI 觉得相关时自动加载
├── UI规范 / 交互原则 / ...
│
第二层：知识沉淀/（生长的经验）
├── 知识索引.md        ← 入口：有什么知识、去哪找
├── 沉淀规范.md        ← 什么时候记、怎么分类
├── 各角色目录/
│   ├── 产品设计/      ← PRD、交互相关经验
│   ├── 增长策略/      ← 投放、转化、实验相关
│   └── AI工程/        ← prompt、工具接入相关
└── 通用知识/          ← 跨角色通用的东西
```

简单说：**Rules 是入职手册，知识沉淀是经验本。**

只有手册没有经验 = 永远停在新人阶段。只有经验没有手册 = 知道很多但不知道自己在哪。两个都要有。

### 知识怎么分：五种类型

| 类型 | 回答什么问题 | 真实例子 |
|------|-------------|---------|
| 经验 | 发生了什么？ | "流量分级方法论有循环论证的坑——用转化率定义质量，又用质量预测转化率" |
| 技能 | 下次怎么操作？ | "增长 PRD 五个必须说清楚：假设、人群、指标、对照、退出条件" |
| 原则 | 应该/不应该做什么？ | "质量定义和效果验证必须分开——用介入前信号定义质量，用转化率验证" |
| 洞察 | 为什么会这样？ | "AI 接到模糊需求时默认'尽可能全面'，用户纠偏几乎总是做减法" |
| 待验证问题 | 还不确定的 | "挽留弹窗效果和弹出时机强相关吗？" |

生成关系：`待验证问题 → 经验 → 技能/原则/洞察`

只写经验不提炼 = 日记。只写原则不留经验 = 后人不知道为什么有这条规则。两步都要做。

### 谁来写？AI 自己写

这是最反直觉的一个设计：**知识内容不是我写的，是 AI 自己写的。**

为什么？因为 AI 是读者。它比我更知道自己需要记住什么、用什么措辞自己更容易理解。

我做的事情是——
- AI 做对了 → "记下来"
- AI 做错了 → "你为什么这么理解？" → 它暴露认知盲区 → 补充知识
- AI 总结出规律 → 我判断对不对，追问为什么

举个例子。有一次我说"做一下本周技能评估"，协作协议里写了知识沉淀的路径，但 AI 没有直接去那个路径，而是从零开始全局搜索，绕了一大圈才找到。事后让它自己复盘，它写了这么一条：

> 加载 ≠ 内化：always_applied rules 每次对话都会加载，但"加载"不等于"形成行动路径"。这和"理解 ≠ 执行"是同一个道理——而这条原则本来是写给 AI 看的，结果 AI 自己犯了这个错。

这种自我反思的角度，我写不出来——因为我不是它的读者。

再举一个。有一次我让 AI 画个流量示意图，它做了一张四层生命周期循环图，超级复杂。我说其实我想看的是分流量类型的漏斗。整个返工。后来的每次反馈都是在做减法。AI 自己总结了一条洞察：

> AI 接到模糊需求时的默认行为是"尽可能全面"，但用户想要的几乎总是最小可用版本。

这就是经验沉淀 → 提炼洞察的完整链路。下次遇到类似场景，AI 会先问"你想要什么形态"，而不是闷头做最复杂的版本。

### 什么时候记？五个触发场景

| 场景 | 为什么值得记 |
|------|------------|
| PRD 多轮修改才达标 | 对业务理解有偏差——偏差本身是经验 |
| 方案被否定重做 | 认知校准的最佳时机 |
| 首次跑通某个流程 | 下次不用重新摸索 |
| 发现反直觉现象 | 最容易忘，也最有价值 |
| 用户纠偏了 AI 的理解 | 不记就会反复犯 |

不用等我提醒，这五条写在协作协议里，AI 做完工作后会自己判断要不要沉淀。

### 开新对话 ≠ 从零开始

有了这套东西之后，最大的变化是——开新对话不可怕了。

知识在文件里，新对话读一下索引就能接上。就像换了个工作台，但工具和经验都还在。

而且有个反直觉的事：**对话越长 ≠ AI 越懂你。** 对话越长 = 干扰越多 = AI 越容易幻觉。正确做法是规划→清空→执行：

1. 规划阶段——充分讨论，吵架，头脑风暴，出方案
2. 清空——产出执行计划文档，开新对话
3. 执行——只读计划文档，按图纸施工

干活时不需要知道开会聊了什么八卦，只需要看图纸。

## 为什么这件事该 PM 来做（3 分钟）

看看这个对照：

| 给 AI 建的 | 给团队建的 |
|---|---|
| Rules（协作协议、产品上下文） | 入职文档、产品手册 |
| 经验 | 复盘会纪要 |
| 技能 | SOP 手册 |
| 原则 | 团队文化、行为准则 |
| 待验证问题 | 待讨论议题 |

完全是同一套能力，载体不同而已——一个放飞书里，一个放 Markdown 文件里。

而且这个过程是双向的。我给 AI 写 Rules 的时候，被迫把"我以为大家都知道"的东西写出来——这个过程让我重新审视了自己给团队沟通时有多少隐性假设没说清楚。

给 AI 构建 context 的能力强了，给人构建 context 的能力也跟着强了。

## 怎么开始（2 分钟）

不需要一开始就搭框架。三步走：

**第一步：写一个 Rule 文件。** 在 `.cursor/rules/` 里建第一个文件，哪怕只写"我们的产品是做 XX 的，用户是 YY"——比什么都不写强一百倍。

**第二步：约定协作规范。** 告诉 AI "遇到不确定的先问我""不要擅自简化需求"。跟你带新人说的话是一样的。

**第三步：开始记东西。** AI 做对了 → 让它记下来。AI 做错了 → 让它复盘为什么，然后记下来。先记再整理，体系在记的过程中自然会长出来。

> Prompt Engineering 解决"这次对话怎么说清楚"，Knowledge Engineering 解决"AI 怎么持续变强"。PM 天然就是做后者的人——因为我们每天都在给人构建 context、管理知识，现在只是多了一个对象。
