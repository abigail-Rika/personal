# 产品经理就是 Context Engineer

> 组内 AI 实践分享 · 大纲 · 预计 30 分钟

---

## 开场：一个发现（3 分钟）

我最近发现一件事：我给 AI 提需求和给研发提需求，踩的坑是一模一样的。

- 需求写模糊了 → 研发做出来不对 → 返工
- Context 给不够 → AI 输出离谱 → 重来

但 AI 比研发"诚实"得多——它不会脑补你没说的东西，不会假装理解了，context 缺什么它就缺什么，反馈还是秒级的。这让我意识到：**我的核心能力不是"写 PRD"，是"构建 context"**——让对方（不管是人还是 AI）在正确的信息环境下做出正确的事。

今天想聊的就是这件事：**产品经理的本质就是 Context Builder。**

---

## Part 1：什么是 Context Building？PM 每天都在做（5 分钟）

先定义一下。Context 不是"信息"，是**经过筛选、组织、有优先级的信息**。

PM 日常工作拆开看，全是 context building：

| PM 的日常动作 | 本质是在做什么 |
|---|---|
| 写 PRD | 给研发构建 context——做什么、为什么做、边界在哪 |
| 需求评审 | 验证 context 是否被正确接收——研发理解的和你想的一样吗？ |
| 写验收标准 | 用最少的信息定义"什么是对的"——context 的压缩 |
| 给老板汇报 | 把大量细节压缩成关键判断——context 的分层 |
| 跨团队对齐 | 让不同背景的人看到同一张图——context 的翻译 |
| 定义数据指标 | 告诉团队"用什么衡量成功"——context 的锚点 |
| 写用户故事 | 把用户的真实场景变成团队能理解的语言——context 的转化 |

**PM 不生产功能，PM 生产 context。功能是研发生产的，但他们能做对，是因为 PM 给了足够好的 context。**

## Part 2：给 AI 构建 context，和给人构建 context 的异同（5 分钟）

### 相同点

1. **信息不够就会出错**
   - 给研发：PRD 漏了一个边界条件 → 上线后出 bug
   - 给 AI：没说清楚业务术语 → AI 用通用理解乱套

2. **太多也会出错**
   - 给研发：PRD 写了 30 页，核心需求淹没在细节里 → 研发抓不住重点
   - 给 AI：一次性塞 50 个文档 → AI 在矛盾信息里迷路（context 溢出）

3. **结构比内容重要**
   - 给研发：同样的信息，按用户故事组织 vs 按功能模块组织，理解效率完全不同
   - 给 AI：同样的信息，分层喂入（先大背景 → 再具体任务）vs 一股脑扔进去，输出质量差很大

### 不同点

| 维度 | 给人 | 给 AI |
|---|---|---|
| 反馈周期 | 评审会、开发中、测试后，周级 | 秒级，说完就能看到结果 |
| 容错 | 人会脑补、会来问你 | AI 不会，缺什么就缺什么 |
| 修正成本 | 返工成本高 | 重新给 context 成本几乎为零 |
| 记忆 | 人有长期记忆，说过一次就记住了 | 每次对话从零开始（除非你主动管理） |

**核心洞察：AI 是 context building 能力的"放大镜"——你的 context 能力强，AI 就强；你的 context 能力弱，AI 立刻暴露你。**

## Part 4：从 Context Building 到 Knowledge Engineering（7 分钟）

> 这是分享的升华部分——从"给一次 context"到"建一套知识体系"

### 一次性 context vs 持久 context

前面聊的都是"给一次 context"——写一次 PRD、填一次 prompt、开一次会。但有个问题：**每次对话结束，AI 就忘了一切。** 你精心构建的 context，下次还得再来一遍。

这就像一个永远在入职第一天的新人——每天早上都从"你好我是 XX"开始。能力不差，但没有积累。

### Agent 不是菜，他只是不知道

最近看到一个说法，很精准：

> "很多人把 agent 用不好归结为 prompt 没写好，然后去研究 prompt engineering。这有用，但解决的是'怎么把一个问题问清楚'，不是'agent 缺什么知识'。prompt engineering 优化的是单次对话的表达效率，knowledge engineering 解决的是 agent 的认知基础。前者是战术，后者是战略。"

### Context 和 Knowledge 的关系

这两个词听起来很像，但解决的问题不同：

| | Context（教科书） | Knowledge（田野笔记） |
|---|---|---|
| 装的是什么 | 产品是什么、UI 长什么样、业务背景 | 这次踩了什么坑、下次怎么做、为什么会这样 |
| 谁来写 | 你写，你维护 | AI 写，你纠偏 |
| 变化频率 | 低——产品背景不会天天变 | 高——每次协作都可能产生新的 |
| 类比 | 新人入职时的产品手册 | 新人做了半年项目后攒的经验本 |

只有 Context 没有 Knowledge = 永远停在"读完手册的新人"。
只有 Knowledge 没有 Context = 经验丰富但不知道自己在哪家公司。
**两者配合 = AI 既懂背景，又有经验，而且越用越好。**

### 我的实践：三个阶段

**第一阶段：只写 Rules（Context）**

给 AI 写协作协议（"怎么和我配合"）、产品上下文（"我们的产品是什么"）、UI 规范（"按钮该长什么样"）。这已经比什么都不写强一百倍了。

**第二阶段：发现 Rules 不够**

Rules 解决的是"不变的规则"。但有一类知识是在协作中生长的——PRD 写了三版才过的教训、AI 理解错业务概念的 gap、第一次接入新工具的流程。这些**经验性知识**，Rules 装不下，对话结束就丢了。

**第三阶段：搭知识体系（Knowledge）**

于是搭了一套知识沉淀框架——

```
知识沉淀/
├── 知识索引.md            # 总索引：有什么知识、去哪找
├── 沉淀规范.md            # 什么时候记、怎么分类
├── 各角色目录/             # 按工作角色分
│   ├── 产品设计/           # 做产品设计时的经验
│   ├── 增长策略/           # 做增长时的经验
│   └── AI工程/            # 搞 AI 协作时的经验
└── 通用知识/               # 跨角色通用的原则和洞察
```

每个角色下面，知识分五种：

| 类型 | 回答什么问题 | 举例 |
|------|-------------|------|
| **经验** | 发生了什么？ | "前测实验一道题等于没做，要三道题才有筛选效果" |
| **技能** | 下次怎么做？ | "落地页 PRD 的标准 checklist" |
| **原则** | 应该/不应该做什么？ | "方案先画状态机，不要直接画页面" |
| **洞察** | 为什么会这样？ | "需求越模糊，AI 越做'安全但平庸'的方案" |
| **待验证问题** | 我还不确定的 | "挽留弹窗效果和弹出时机强相关吗？" |

**关键**：这些内容不是我写的——是让 AI 自己写的。我做的是在它做对时说"记下来"，做错时问"你为什么这么理解"。AI 比我更知道自己需要记住什么——因为它是读者。

**而且开新对话不等于从零开始。** 知识已经沉淀在文件里了，新的对话读一下索引就能接上——就像换了个工作台，但工具和经验还在原来的地方。

### 类比：给团队建 wiki

仔细想想，这和 PM 在团队里做的事一模一样：

| 给 AI 建的 | 给团队建的 |
|---|---|
| Rules（协作协议、产品上下文） | 入职文档、产品手册 |
| 经验 | 复盘会纪要 |
| 技能 | SOP 手册 |
| 原则 | 团队文化、行为准则 |
| 待验证问题 | 团队待讨论议题 |

**PM 给团队构建的知识体系，和给 AI 构建的知识体系，本质上是同一套能力。** 区别只是载体不同——一个放在 Notion/飞书里，一个放在 Markdown 文件里。

## Part 5：技术平权之后，PM 的壁垒在哪？（3 分钟）

### 技术壁垒正在消失

以前产品经理可以靠"我们有独家模型/独家数据"构建产品壁垒。但当模型能力趋同、框架开源、接入成本降低后，这层壁垒几乎消失了。

### PM 未来的三个核心壁垒——全是 Context Building

| 壁垒 | 含义 | 和 context building 的关系 |
|---|---|---|
| **场景翻译能力** | 把模糊的用户需求翻译成 AI 可执行的精确指令 | 你做的 prompt 工程、写的 Rules，本质都是"场景沉淀 → 精确指令" |
| **体验设计能力** | 模型能力相同时，谁的交互更自然、反馈更及时，决定用户留不留 | 技术趋同后体验差距被放大，体验设计的前提是理解用户 context |
| **数据闭环能力** | 不是拥有数据，而是知道怎么用数据迭代产品 | "用数据驱动决策"比"拥有数据"更值钱 |

**技术平权让所有人站在同一起跑线上。跑出差距的，是你对场景的理解深度——也就是你构建 context 的颗粒度。**

## 收尾（2 分钟）

一句话总结：

> **产品经理的核心能力不是写文档、不是画原型、不是做数据——是构建 context。AI 时代只是把这个真相放大了：你构建 context 的能力有多强，你能撬动的产出就有多大。**

以前你只能给人构建 context，现在你还可以给 AI 构建 context。杠杆从"一个团队"变成了"一个团队 + 无限的 AI 算力"。

而且，这不是一次性的事。**Context 不是写一次就完了——它会生长。** 每一次协作中的纠偏、踩坑、跑通，都可以沉淀为知识，让下一次协作更好。从 Prompt Engineering（把这次对话说清楚）到 Knowledge Engineering（让 AI 持续积累），是 PM 用 AI 的下一个台阶。

**如果你想开始，不需要搭什么框架——打开 Cursor，在 .cursor/rules/ 里写第一个 .mdc 文件就行。** 哪怕只写一句"我们的产品是做 XX 的"，也比什么都不写强一百倍。剩下的，在用的过程中自然会长出来。
