## 一句话定位

> 主导大促期间增长基建支撑，落地页流程优化 + 双端联动 H5 抽奖系统设计，打通直播间与 H5 同一配置/同一奖池/同一开奖结果，承接微信场景已下单用户参与抽奖 + 未下单用户的下单转化。

## S · 背景（Situation）

**业务背景**：海豚 AI 学每月有大促活动（直播间为主战场），需要把直播间的抽奖福利同步到 H5 端，让微信场景下的用户也能参与，同时把 H5 作为未下单用户的转化入口。

**核心痛点**：
- **落地页问题**：原流程要用户先选礼品再提交预约，分两步操作，预约率 80%+ 但仍有 20% 流失
- **H5 抽奖问题**：直播间已有自研抽奖系统（Gaffey 后台），但 H5 端没有承接，导致：
  - 微信场景下的已下单用户错失抽奖参与，氛围感弱
  - 未下单用户没有"下单抽奖"的强抓手
- **双端不联动**：直播间和 H5 是两套独立系统，配置、开奖结果都要重复维护

---

## T · 目标（Task）

**北极星指标**：
- 落地页预约率从 80%+ 提升（具体目标待补充）
- H5 抽奖参与率（已下单用户）/ 下单转化率（未下单用户）达到业务方预期（具体目标待补充）

**KR 拆解**：
- KR1：落地页预约+礼品选择整合到单页，去掉 20% 流失
- KR2：H5 抽奖系统上线，双端展示一致（同一配置/同一奖池/同一开奖结果）
- KR3：未下单用户的"下单抽奖"链路打通（CTA → 下单页 → 资格回写 → 参与）

**不追求什么**：
- 不重做直播间侧的抽奖能力（复用现有 Gaffey 后台）
- 不要求 H5 用户实时在线（进入时加载当前状态即可）
- 不做"点击即预约"（保留明确提交动作，避免数据虚高）

## A · 行动（Action）

### 决策 1：落地页"预约+礼品"整合到单页 + 保留提交按钮

- **面对的问题**：原两步流程预约率高但仍有 20% 流失，是把流程压缩还是优化激励？
- **备选方案**：
  - A. 整合到单页 + 保留提交按钮
  - B. 整合到单页 + 点击礼品即预约（最激进）
  - C. 维持两步，优化文案/视觉
- **最终选择**：A
- **依据**：
  - B 的"点击即预约"会让数据虚高（用户只是好奇点了一下也算预约），后续转化反而崩
  - 用户体验上保留明确提交动作，给用户充分选择空间
  - C 的边际收益太小，已经 80%+ 没什么改进空间
- **结果**：方案对齐，按钮文案"提交并预约"，待开发上线

### 决策 2：H5 抽奖采用"读取直播间后台同套配置"架构，不新建抽奖引擎

- **面对的问题**：H5 抽奖是独立建一套系统，还是复用现有直播间能力？
- **备选方案**：
  - A. 独立建一套 H5 抽奖引擎
  - B. 读取 Gaffey 后台同一套配置和数据，H5 只做前端
- **最终选择**：B
- **依据**：
  - 直播间侧已有自研抽奖后台，能力成熟（奖品池、中奖人数、倒计时、参与条件、中奖次数等都已具备）
  - 双端用同一套配置可以保证：同一奖池、同一开奖结果、运营只配一次
  - 避免数据/逻辑分裂带来的不一致
  - 后台只需新增 3 项改动：奖品池图片、参与条件「仅下单」、抽奖渠道字段
- **结果**：架构敲定，明确"H5 页面由前端独立开发，后台只负责配置数据和抽奖接口"，把后台改造成本降到最低

### 决策 3：14 项关键决策一次性对齐，避免开发期反复返工

- **面对的问题**：跨系统协作（直播间 + H5 + 后台 + 销售）涉及大量决策，开发期反复对齐会拖延上线
- **行动**：在方案设计期就把 14 项关键决策表面化、文档化、对齐化

| 决策维度 | 关键结论 |
|---------|---------|
| 系统架构 | 复用直播间后台 |
| H5 登录 | 手机号验证码 |
| 资格判定 | 大促期间已下单/续费 = 有资格 |
| 参与方式 | 下单后自动参与所有共有轮次，不需手动操作 |
| 中奖限制 | 整场只中一次，规则不外显 |
| 开奖方式 | 后台自动按时间开奖 |
| 实时性 | 进入 H5 加载当前状态即可，不要求实时在线 |
| 评论轮次 | 直播间专属，H5 不展示 |
| ……（共 14 项） | 详见 PRD |

- **依据**：复杂跨系统项目最大的风险是"边做边对齐"，每个决策点都可能让开发返工
- **结果**：14 项决策书面共识 + 后台改动清单（3 项） + 功能清单（7 项 P0），开发期不需要再开会对齐基础问题

### 决策 4：把"预约成功通知"拆为独立需求，不阻塞主流程

- **面对的问题**：用户预约成功后需要短信+站内信通知，这个能力是绑在落地页项目里，还是独立拆出来？
- **决策**：拆为独立需求
- **依据**：
  - 通知能力不仅服务于落地页场景，未来其他场景也用得上
  - 独立排期可以避免拖延落地页主流程
  - 复用同一套通知逻辑，后续维护成本低
- **结果**：拆分文档化，独立排期推进

## 🎤 面试常见追问 + 标准答案

### Q1：14 项决策对齐这个事看起来很琐碎，凭什么是关键？

**追问意图**：考察项目管理的颗粒度认知
**标准答案**：
- 跨系统项目（直播间+H5+后台+销售）的最大风险不是技术问题，是"决策点没对齐导致返工"
- 14 项决策中有些是"看起来不重要但开发到一半才暴露"的，比如：
  - 中奖限制规则要不要外显？这影响 H5 文案、用户预期、客诉风险
  - 实时性要求？这决定后端架构（轮询 vs 推送）
  - 评论轮次同步不同步？这影响 H5 展示逻辑
- 我的经验是：**决策不在 PRD 里写清楚，开发就会按自己的理解做，最后大概率和业务方/运营预期不符**
- 把这些决策做成"在线表格"，业务方一项一项确认，比开 3 个会更高效

### Q2：你为什么选择"复用直播间后台"而不是"独立建一套"？业务方有压力让你重做吗？

**追问意图**：考察架构判断和向上管理
**标准答案**：
- 选择复用是综合三个判断：
  1. **能力成熟度**：直播间抽奖跑了多次大促，能力已经验证，现成的能用
  2. **双端一致性**：用户在 H5 看到的开奖结果必须和直播间一样，这是产品体验底线，独立两套很容易不一致
  3. **维护成本**：运营每次大促配一次 vs 配两次，长期看维护成本差异巨大
- 业务方一开始确实倾向"H5 完全独立、想做啥做啥"，我的应对是：
  - 先识别他们真正的诉求："完全独立"不是目的，"想做啥做啥"才是
  - 然后用 3 项后台改造（图片、参与条件、抽奖渠道）覆盖了 95% 的"想做啥"需求
  - H5 前端独立开发，UI 想怎么做就怎么做——没限制业务方的灵活度

### Q3：落地页那个 20% 流失你怎么知道是流程问题，不是其他原因？

**追问意图**：考察数据敏感度和归因能力
**标准答案**：
- 这个判断需要补充确认（说实话，当时业务方反馈"流程繁琐导致流失"，我没做更深的归因）
- 如果让我重做，会做的归因步骤：
  1. **看流失环节分布**：是停在"选礼品"还是"提交"？两个环节流失模式不同
  2. **用户调研**：访谈 5-10 个流失用户，问真实原因（可能是礼品不吸引、信任度不够、操作太麻烦）
  3. **数据细分**：按渠道/年级/设备拆，是不是某类用户流失尤其严重
- 现在的方案"整合到单页"是低成本试错——如果流失原因真的是流程，整合后会有效；如果是其他原因，至少不会让事情变糟。但这是直觉判断，不是数据驱动
