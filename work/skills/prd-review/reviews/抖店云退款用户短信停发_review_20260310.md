# PRD Review：抖店云退款用户收到短信问题修复

> 版本：v1 | PRD 类型：🟢快速验证（bug 修复） | Review 深度：标准 | 日期：2026-03-10

## 门禁判断

⚠️ 方向正确，但有 2 个阻塞点需要补充后才能交付研发：
1. **退款状态值未确认**——PRD 原文写了"mainStatus 是否为 21/22/39← cur 老师说的，不包准"，这是核心逻辑，不能带着"不包准"交给研发
2. **缺少验证方案**——修完之后怎么确认 fix 生效了？

## 各维度评价

### 1. 用户视角
- **判断**：⚠️
- **评价**：PRD 从技术/业务视角描述（"短信恢复后发现问题"），没有从用户感受出发。实际上用户体验很差——已经退款了还天天收到催激活短信，容易产生负面情绪甚至投诉。这一点值得写进去，因为它能让研发理解"为什么这个 bug 值得优先修"。
- **领导可能会问**：有用户投诉吗？退款用户收到短信后有没有差评或二次投诉？
- **改进思路**：开头加一句用户视角的问题描述，比如"用户已退款，仍在 7 天内持续收到催激活短信，造成困扰"。如果有实际投诉数据就附上。

### 2. 问题定义
- **判断**：✅
- **评价**：问题清晰——退款用户仍收到催激活短信。有实际 case 佐证（3 月 2 日下单当天退款，3 月 4 日仍收到短信）。作为 bug 修复，这个粒度够了。

### 3. 问题分析
- **判断**：✅
- **评价**：根因分析到位——触发逻辑只校验 `ariesOrderId ≠ 0`，不检查退款状态。三个触发组件（RedemptionNotifyReminder、DouyinSmsNotifyReminder、DouDianSendSmsJob）都有这个问题。这部分是莫森宇梳理的，技术根因明确。

### 4. 收益判断
- **判断**：⚠️
- **评价**：PRD 没有写收益。虽然 bug 修复的收益"显然"是止损，但缺少量级感知。
- **领导可能会问**：每天有多少退款用户在收到无效短信？短信成本浪费了多少？
- **改进思路**：补一个简单的影响面估算——日均退款订单量 × 最多 11 条 = 浪费的短信量。不需要很精确，有量级感知就行。

### 5. 是否直击根本
- **判断**：✅
- **评价**：在触发逻辑中加退款状态校验，直接解决根因，方案和问题复杂度匹配。

### 6. 竞品/行业参照
- **判断**：N/A
- 这是内部 bug 修复，不需要竞品参照。

### 7. 方案路线对比
- **判断**：N/A
- bug 修复方案唯一（在触发处加校验），不需要对比。

### 8. 效果评估思路
- **判断**：❌
- **评价**：完全缺失。修完之后怎么知道 fix 生效了？
- **改进思路**：至少要有：
  1. **测试方案**：找一个已退款的测试订单，验证不再触发短信
  2. **线上验证**：上线后监控退款用户的短信发送量，确认降为 0
  3. **观察周期**：建议观察 7 天（覆盖一个完整的 D0~D6 周期）

### 9. 待决策点
- **判断**：⚠️
- **评价**：PRD 暴露了一个关键未决项（mainStatus 的值"不包准"），态度诚实，但这个不能带着模糊上线。此外还有隐藏的待决策点没提出来。
- **隐藏的模糊点**：
  1. **存量处理的"立即停发"怎么实现？**——D1~D6 的短信是通过 ReminderJob/DouDianSendSmsJob 定时触发的，"立即停发"是指改完逻辑后自然生效（因为每次触发前都会重新校验），还是需要额外清理已经排入队列的任务？这个需要和研发确认。
  2. **用户激活后是否也应该停发？**——现状描述是"一直不激活"的场景。如果用户在 D0 退款但 D3 又重新下单并激活了呢？虽然不在本次修复范围内，但值得确认边界。

## 修改优先级

1. **【必须】确认 mainStatus 退款状态值**——找莫森宇/丰哥确认具体值，去掉"不包准"，这是开发的前置条件
2. **【必须】补效果验证方案**——至少写明测试方案和线上观察指标
3. **【建议】补影响面数据**——日均退款量 × 短信条数，给优先级判断提供依据
4. **【建议】和研发确认"存量立即停发"的实现方式**——是逻辑修改后自然生效，还是需要额外操作

## 给你的建议

PRD 整体结构清晰，现状梳理和根因分析都不错（特别是把 11 条短信时间线和触发机制写清楚了，这让研发能快速理解改哪里）。

核心提升点：**bug 修复类 PRD 容易写成"现状 + 改法"就完了**，但领导关心的不只是"改不改"，还有"改完怎么验证"和"影响面多大"。加上这两块，PRD 就完整了。

另外，"不包准"这种表述虽然真实，但出现在正式 PRD 里会让评审人觉得你没做完功课。建议改成"待研发侧确认具体状态值"——意思一样，但呈现出来是"我知道这里需要确认，已经安排了"，而不是"我也不确定"。
