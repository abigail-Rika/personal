# PRD Review

以**产品 Leader 的视角**预审你的 PRD，帮你提前发现会被挑战的点，并给出具体的改进思路。

### 定位

- **视角**：站在领导的位置，用她的标准和维度来看你的 PRD
- **目的**：不只是告诉你"哪里有问题"，更重要的是告诉你"怎么改"和"怎么回答领导的追问"
- **角色**：既是门禁判断者（这个 PRD 能不能过），也是教练（帮你提升思考深度）

### 与 prd-writer 的关系

- **prd-writer**：从你自己的视角出发，帮你思考和写作
- **prd-review**（本文件）：从领导的视角出发，模拟 review 给反馈
- 建议流程：先用 writer 写完 → 再用 review 自我预审 → 修改后提交正式 review

v1 审问题分析与方案方向，v5 审交互设计。

## 工作流

### Step 1：获取 PRD 内容

**Confluence 文档**（v1/v5 均适用）：

```
MCP server: user-shimo
Tool: get_confluence_content
Arguments: { "page": "<url>", "pageId": "<id>" }
```

**Motiff 设计稿**（v5 交互稿）：

从 Motiff URL `https://motiff.com/file/{docId}?nodeId={nodeId}` 中提取参数。nodeId 中的 `%3A` 需解码为 `:`。

```
MCP server: user-motiff
Tool: get_motiff_node_screenshot  # 获取设计截图
Arguments: { "docId": "<docId>", "nodeId": "<nodeId>" }

Tool: get_motiff_node             # 获取 HTML 结构（辅助分析布局和组件）
Arguments: { "docId": "<docId>", "nodeId": "<nodeId>" }
```

用户可能同时提供 Confluence 链接和 Motiff 链接，都需要拉取。

### Step 2：识别版本

从 PRD 标题中的版本号判断：
- 标题格式：`产品名X.X-{159版本}-{副版本}`，如 `通用题库 CMS1.0-1-3` 中 `-1-` 表示 v1
- 版本 1 = v1 概念稿，5 = v5 主功能稿，9 = v9 细节稿
- 无法判断时问用户
- v9 不在 review 范围内，如果是 v9 告知用户

### Step 3：识别 PRD 类型 & 评估 Review 深度

#### PRD 类型判断

先识别 PRD 属于哪种类型，review 侧重点不同：

| 维度 | 🟢 快速验证型 | 🔵 完整方案型 |
|------|-------------|-------------|
| 典型场景 | 短期活动、低成本实验、运营抓手 | 产品功能新增/重构、流程重设计 |
| 开发周期 | ≤1 周或纯配置 | >1 周 |
| 失败成本 | 低（可回滚/有时限） | 高（浪费资源/影响体验） |

**🟢 快速验证型的 review 核心**：不需要追问很深的用户分析和根因挖掘，重点看三件事：
1. **有效性**：为什么认为这个方案能起作用？
2. **成本可控**：开发和运营成本是否合理？
3. **无副作用**：会不会造成用户认知混乱、破坏现有体验、产生难以收回的承诺？

**🔵 完整方案型的 review 核心**：完整覆盖所有 9 个维度，重点在"为什么做"和"为什么这么做"。

#### Review 深度

**深度 review**（每个维度详细分析，给具体建议）— 满足任一条件：
- 影响核心业务指标：首单 ROI、UE、体验课转化率、在课留存（周完习率）、长续率、退费率
- 影响全量用户（而非小部分用户）
- 涉及多个部门协作
- 改动范围大（多个模块/页面）
- 开发难度高

**标准 review**（标注有问题的维度，给要点）：不满足上述条件。

无法判断时问用户："这个需求的影响面和复杂度大概是什么水平？"

### Step 4：按版本 Review

详细检查标准见 [review-checklist.md](review-checklist.md)。

#### v1 Review：问题分析与方案方向

核心判断：**问题值得做吗？方向对吗？**

| # | 维度 | 核心问题 | 🟢快速验证 | 🔵完整方案 |
|---|------|---------|-----------|-----------|
| 1 | **用户视角** | 需求从用户出发吗？对用户影响说清楚了吗？ | 重点看**无副作用** | 深入分析 |
| 2 | 问题定义 | 要解决什么问题？ | 简要即可 | 必须清晰 |
| 3 | 问题分析 | 做了严肃分析吗？ | 点到即可 | 至少 2-3 层 why |
| 4 | 收益判断 | 收益清晰吗？ | 重点看**成本可控** | 完整 ROI |
| 5 | 是否直击根本 | 方案解决根因吗？ | 可接受"绕过根因的低成本试验" | 必须直击 |
| 6 | 竞品/行业参照 | 别人怎么做的？ | 有更好，没有不强求 | 必须有 |
| 7 | 方案路线对比 | 想过其他路线吗？ | 不需要和重方案对比 | 必须对比 |
| 8 | 效果评估思路 | 怎么知道成功了？ | 重点看**有效性论证** | 完整评估 |
| 9 | 待决策点 | 还有模糊点吗？ | 标准不变 | 标准不变 |

**关于「用户视角」在不同类型中的应用**：
- 🔵 完整方案型：这是贯穿 review 的底层检查，需要回归用户需求，说清楚用户影响和体验变化
- 🟢 快速验证型：不需要深入用户分析，但必须确认方案**不会造成副作用**——不会导致用户认知混乱、不会破坏现有体验、不会产生难以收回的长期承诺。如果一个"低成本试验"会把某个功能误用导致用户对产品产生误解，那即使成本低也不应该做

**门禁判断：**
- ✅ 可以推进到 v5
- ⚠️ 需要在特定点上补充后重新 review
- ❌ 方向有问题，建议重新分析

#### v5 Review：交互设计

前提：v1 方向已过。核心判断：**交互走得通吗？设计合理吗？**

| # | 维度 | 核心问题 |
|---|------|---------|
| 1 | 场景还原 | 主流程走得通吗？（谁→页面→看到什么→想做什么→怎么操作） |
| 2 | 交互逻辑自洽 | 各功能点正常逻辑是否清晰、自洽 |
| 3 | 与 v1 方向一致 | 交互方案是否忠实于 v1 定的方向 |
| 4 | 设计一致性 | 是否复用已有组件和交互模式，避免不必要的新发明 |
| 5 | 交互层待决策点 | 有没有交互设计上拿不准的地方 |

**门禁判断：**
- ✅ 可以推进到 v9 交付开发
- ⚠️ 需在 v5 上修改（方向没变）
- ❌ 方向变了，回到 v1

### Step 5：输出 Review 报告

```markdown
# PRD Review：{PRD 名称}

> 版本：{v1/v5} | PRD 类型：{🟢快速验证/🔵完整方案} | Review 深度：{深度/标准} | 日期：{YYYY-MM-DD}

## 门禁判断

{一句话结论}

{如果不通过，列出阻塞原因}

## 各维度评价

### 1. {维度名称}
- **判断**：✅ / ⚠️ / ❌
- **评价**：{具体说明，引用 PRD 中的原文佐证}
- **领导可能会问**：{模拟领导的追问，帮 PM 提前准备}
- **改进思路**：{具体的改法——不是"分析不够深"，而是"你可以从 XX 角度补一段，具体写法是..."}

（重复各维度）

## 修改优先级

{按重要性排序，告诉 PM 先改什么、后改什么，哪些可以快速补、哪些需要花时间想}

## 给你的建议

{教练式建议：肯定做得好的地方，指出核心提升点，示范"如果是我会怎么想这个问题"}
```

### Step 6：存档

保存到：`prd/prd-review/reviews/{PRD名称}_review_{YYYYMMDD}.md`

如果目录不存在，创建目录。

## 注意事项

- 始终以**领导视角**出发，但目的是帮 PM 变强，不是挑刺
- 评价要具体、引用原文，不说空话
- **改进建议要可操作**——不是"问题分析不够深"，而是"你分析到了到习完习 90%+，但没追问'那为什么不到习'，可以从 XX 角度补一段"
- 给出**领导可能的追问**，帮 PM 提前准备回答
- 区分 PRD 类型：🟢快速验证型不要用🔵完整方案型的标准来过度要求
- 不纠结 v9 层面的细节（异常状态、loading、文案等），那不是 review 重点
- 业务核心指标参考：首单 ROI、UE、体验课转化率、在课留存、退费率
