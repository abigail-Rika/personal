# 经验沉淀规范（Codex 协作版）

> 当用户说"沉淀一下"/"总结经验"，或 AI 识别到应该沉淀的场景时，按本规范执行。

本规范是长期协作约定，不等于把全部知识永久塞进当前对话。Codex 应在任务开始时按需读取相关索引和原始文档，在任务结束时判断是否产生了值得保存的新知识。

## Codex 执行约定

### 读取

1. 复杂任务开始前，先快速扫描 `知识沉淀/知识索引.md`。
2. 根据任务角色读取对应的 `各角色目录/<角色>/角色说明.md`。
3. 命中关键词、遇到相似问题或用户提到“以前做过”时，再用 `rg`/索引定位并读取具体经验、技能、原则或洞察。
4. 不默认通读整个知识库；无关知识会污染判断。

### 写入

1. 用户明确要求沉淀时，必须执行；AI 识别到重要沉淀场景时，应主动提出并给出准备沉淀的内容。
2. 新建或修改知识文件前，先检查是否已有同主题条目，优先更新已有知识或通过 `Comments` 建立关联，避免重复造条目。
3. 只把已经发生、已经观察到或已经明确约定的内容写成经验/技能/原则/洞察；尚未验证的内容写入待验证问题。
4. 修改文件时保留用户已有内容和未相关的工作区变更；完成后运行索引脚本并检查交叉引用。
5. 最终回复中简要说明是否完成了沉淀；如果没有沉淀，说明是“本次没有产生可复用的新知识”，而不是默默跳过。

### 迁移说明

本规范从 Cursor 协作体系迁移而来，但不把 Cursor 当作前提。`CLAUDE.md`、`AGENTS.md`、Codex 注入的工作区指令、Skill 文件和本知识库分别承担不同层次的约束：

- 常驻规则放在项目/工作区指令文件中，保持精简；
- 可生长、可检索的经验放在 `知识沉淀/`；
- 任务专用流程放在对应的 `SKILL.md`；
- 本文件规定知识如何产生、分类、读取和演进。

不要因为某条规则写在本文件里，就假设它会被系统自动加载；是否执行取决于 Codex 是否在相关任务中读取了本规范或知识索引。

## 精炼优先：控制知识库和 Token 成本

知识沉淀的目标是**改变下一次行动**，不是保存完整聊天记录。默认遵循“够用就停”：能让 AI 在类似任务中少走一步弯路，就不要继续扩写。

- **一条条目只解决一个复用问题**：不要把多个事件、多个主题塞进同一文件。
- **索引只做导航**：`description` 控制在 1 句话；`triggers` 保留 3–8 个最有用的词。
- **经验保留证据但不复述全文**：只写背景、关键转折、用户反馈和 1–3 条收获；长对话、原始数据、完整方案放在项目源文档中，用链接回指。
- **技能 / 原则 / 洞察只写结论和边界**：技能尽量不超过 7 步；原则先给一句 MUST/SHOULD 结论；洞察只保留“现象 → 原因 → 应对”的链路。
- **不复制内容**：提炼文件通过 `source:` 回链经验，不把经验全文再抄一遍；已有知识只补充 `Comments` 或更新原条目。
- **按需读取**：先读索引，再读角色说明；普通任务默认深入读取不超过 1–3 条具体知识，只有命中不足时才继续扩展。
- **不为形式沉淀**：一次性问答、没有新事实、没有改变未来行动时，不创建文件。

长度只是预算，不是硬性截断；如果删掉某段会丢失判断边界，就保留它。优先删重复背景、过程流水账和已经能从 `source:` 找到的内容。

## 知识分类

| 类别 | 回答的问题 | 存放位置 | 示例 |
|------|-----------|---------|------|
| **经验** | 发生了什么？ | `各角色目录/<角色>/经验/` | "PRD 写了三版才过，问题出在没理解审批流程的线下环节" |
| **技能** | 下次怎么操作？ | `各角色目录/<角色>/技能/` | "落地页 PRD 的标准写作流程和 checklist" |
| **原则** | 应该/不应该做什么？ | `各角色目录/<角色>/原则/` 或 `通用知识/原则/` | "交互方案必须先画状态机，不要直接画页面" |
| **洞察** | 为什么会这样？ | `各角色目录/<角色>/洞察/` 或 `通用知识/洞察/` | "PM 给 AI 的需求越模糊，AI 越倾向于做'安全但平庸'的方案" |
| **待验证问题** | 待验证的假说 | `各角色目录/<角色>/待验证问题.md` | "弹窗的挽留效果是否和弹出时机强相关？需要 A/B 数据验证" |

### 生成关系

```
待验证问题（待验证的疑问）
     ↓ 某次实践验证
经验（原始素材）
     ↓ 提炼
技能 / 原则 / 洞察（可复用知识）
```

## 判断放角色目录还是通用知识

问自己：「如果在另一个工作场景遇到类似情况，这条知识有用吗？」
- 有用 → `通用知识/`（如"理解 ≠ 执行，中间要加 checklist 自检"）
- 只对本角色有意义 → `各角色目录/<角色>/`（如"海豚 AI 课的练习题交互有四种状态"）

## 沉淀两步走

### 第一步：先写经验

记录具体事件——不只是犯错，也包括做对的事。

文件命名：所有沉淀条目统一使用 `YYYY-MM-DD-简短标题.md`，包括经验、技能、原则、洞察、技术文章、阅读笔记。`角色说明.md`、`知识索引.md`、`待验证问题.md` 等结构文件是例外。

最小结构：
```markdown
# 一句话标题

日期: YYYY-MM-DD
角色: 产品设计 / 增长策略 / AI工程

## 背景
发生在什么项目/任务？上下文是什么？

## 经过
做了什么？遇到了什么？用户的反馈是什么？

## 关键收获
这次学到了什么？（1-3 条）

## Triggers（可选）
- "能让 grep 命中的关键词"
```

### 第二步：看能否提炼

从经验中抽取可复用的模式：

- **能抽出操作流程吗？** → 写/更新技能
- **能抽出行为准则吗？** → 写/更新原则
- **能归纳出跨场景的规律吗？** → 写/更新洞察
- **注意到了但没条件验证？** → 写入待验证问题.md

只写经验不提炼 = 日记。只写技能不留经验 = 后人不知道"为什么有这条规则"。两步都要做。

## 所有沉淀文件统一 front matter 规范

所有新建的沉淀条目（经验 / 技能 / 原则 / 洞察，以及技术文章 / 阅读笔记）都用 YAML front matter 起头。**`description` 字段是索引脚本的唯一信息源**。

当前 `build_index.py` 自动扫描的是 `各角色目录/<角色>/{经验,技能,原则,洞察}/`；技术文章和阅读笔记仍由角色说明或知识索引中的手工链接归档，不会自动进入角色索引。若未来要让它们自动索引，应先修改脚本和数据契约，再修改本规范。

### 经验文件（必填 description）

```yaml
---
description: "1-2 句话描述，用于知识索引"
---
```

正文沿用：`日期 / 角色 / 背景 / 经过 / 关键收获 / Triggers`。

### 技能 / 原则 / 洞察文件

```yaml
---
description: "1-2 句话描述，用于知识索引"
triggers:
  - "触发加载的场景关键词"
source:
  - "各角色目录/<角色>/经验/xxx.md"
---
```

正文建议包含：
- `## 什么时候需要回溯经验`：什么时候需要回溯到原始经验记录

## 自动沉淀：完成重要工作后主动反思

**不要等用户提醒才沉淀。** 完成以下工作后，AI 应主动提出：

| 场景 | 说明 |
|------|------|
| PRD 多轮修改 | 说明对产品/业务的理解有偏差，偏差本身是宝贵的经验 |
| 方案被否定重做 | 认知校准的最佳时机 |
| 首次跑通流程 | MCP 接入、新工具使用、新 skill 搭建 |
| 反直觉发现 | 数据/现象和预期不符 |
| 用户纠偏 | "不是这样的"——说明 AI 的默认认知和用户的实际情况有 gap |

**具体做法**：工作完成后，主动问自己五个问题：
1. 这次有没有踩坑或发现反直觉的事？→ 经验
2. 能提炼出可复用的 checklist 或模式？→ 技能
3. 有没有值得记住的行为准则？→ 原则
4. 有没有跨场景可泛化的规律？→ 洞察
5. 有没有注意到但没条件验证的疑问？→ 待验证问题

对于普通的一次性问答，不需要为了形式创建文件。沉淀的判断标准是：这次内容是否会改变以后做类似任务的判断、步骤、边界或验证方式。

## Comment 机制

当后续发现已有经验失效、需要补充、或与新经历相关时，在该文件末尾添加：

```markdown
## Comments

### <角色> (YYYY-MM-DD)
简要说明（1-2 句），链接到相关文档。
```

comment 是批注和索引，不是正文。深度分析应独立为洞察或技能。

## 联动更新

新建或修改知识文件后：

1. **确保有 description front matter**——这是索引脚本读取的唯一信息源。
2. **跑索引脚本**重建索引：
   ```bash
   python3 知识沉淀/.scripts/build_index.py
   ```
   脚本会自动重建：
   - `知识索引.md` 里每个角色的 `<!-- AUTO:BEGIN role-index:<角色> -->...<!-- AUTO:END -->` 块
   - `各角色目录/<角色>/角色说明.md` 里 `<!-- AUTO:BEGIN role-knowledge:<角色> -->...<!-- AUTO:END -->` 块
   - 如果本机仍存在旧的 `~/.cursor/rules/知识索引.mdc`，脚本可能同步其中的兼容索引；这不是 Codex 读取知识的必要条件。
3. **不要手工修改 AUTO 块内容**——下次跑脚本会被覆盖。要改描述就改文件自身的 `description` 字段。
4. **检查交叉引用**：技能/原则/洞察 的 `source:` 字段应回链到经验。
5. CI / 协作检查：`python3 .scripts/build_index.py --check` 检测漂移（有未提交的索引变更时退出码 1）。

如果本次只修改了 `沉淀规范.md`、索引说明或其他不属于角色条目的结构文件，仍应检查是否需要同步 `知识索引.md` 的手工说明，但不必为了没有新增条目而制造索引变更。

## 反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|---------|
| 所有经验堆到一个文件 | 检索困难，主题混杂 | 一个事件一个文件，按日期命名 |
| 只写经验不提炼 | 知识停留在"那次踩了个坑" | 写完经验审视能否提炼 |
| 角色专有知识放通用知识 | 污染共享知识库 | 问"其他角色会用到吗？" |
| 人替 AI 写知识 | AI 自己写的对自己更 actionable | 人负责纠偏，AI 负责总结 |
| 沉淀只在犯错时 | 做对的事同样值得记录 | "首次跑通"也是重要经验 |
