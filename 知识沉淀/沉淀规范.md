# 经验沉淀规范

> 当用户说"沉淀一下"/"总结经验"，或 AI 识别到应该沉淀的场景时，按本规范执行。

## 知识分类

| 类别 | 回答的问题 | 存放位置 | 示例 |
|------|-----------|---------|------|
| **经验** | 发生了什么？ | `各角色目录/<角色>/经验/` | "PRD 写了三版才过，问题出在没理解审批流程的线下环节" |
| **技能** | 下次怎么操作？ | `各角色目录/<角色>/技能/` | "落地页 PRD 的标准写作流程和 checklist" |
| **原则** | 应该/不应该做什么？ | `各角色目录/<角色>/原则/` 或 `通用知识/原则/` | "交互方案必须先画状态机，不要直接画页面" |
| **洞察** | 为什么会这样？ | `各角色目录/<角色>/洞察/` 或 `通用知识/洞察/` | "PM 给 AI 的需求越模糊，AI 越倾向于做'安全但平庸'的方案" |
| **待验证问题** | 待验证的假说 | `各角色目录/<角色>/待验证问题.md` | "弹窗的挽留效果是否和弹出时机强相关？需要 A/B 数据验证" |

### 生成关系

```
待验证问题（待验证的疑问）
     ↓ 某次实践验证
经验（原始素材）
     ↓ 提炼
技能 / 原则 / 洞察（可复用知识）
```

## 判断放角色目录还是通用知识

问自己：「如果在另一个工作场景遇到类似情况，这条知识有用吗？」
- 有用 → `通用知识/`（如"理解 ≠ 执行，中间要加 checklist 自检"）
- 只对本角色有意义 → `各角色目录/<角色>/`（如"海豚 AI 课的练习题交互有四种状态"）

## 沉淀两步走

### 第一步：先写经验

记录具体事件——不只是犯错，也包括做对的事。

文件命名：所有沉淀条目统一使用 `YYYY-MM-DD-简短标题.md`，包括经验、技能、原则、洞察、技术文章、阅读笔记。

最小结构：
```markdown
# 一句话标题

日期: YYYY-MM-DD
角色: 产品设计 / 增长策略 / AI工程

## 背景
发生在什么项目/任务？上下文是什么？

## 经过
做了什么？遇到了什么？用户的反馈是什么？

## 关键收获
这次学到了什么？（1-3 条）

## Triggers（可选）
- "能让 grep 命中的关键词"
```

### 第二步：看能否提炼

从经验中抽取可复用的模式：

- **能抽出操作流程吗？** → 写/更新技能
- **能抽出行为准则吗？** → 写/更新原则
- **能归纳出跨场景的规律吗？** → 写/更新洞察
- **注意到了但没条件验证？** → 写入待验证问题.md

只写经验不提炼 = 日记。只写技能不留经验 = 后人不知道"为什么有这条规则"。两步都要做。

## 所有沉淀文件统一 front matter 规范

所有类型（经验 / 技能 / 原则 / 洞察）都用 YAML front matter 起头。**`description` 字段是索引脚本的唯一信息源**。

### 经验文件（必填 description）

```yaml
---
description: "1-2 句话描述，用于知识索引"
---
```

正文沿用：`日期 / 角色 / 背景 / 经过 / 关键收获 / Triggers`。

### 技能 / 原则 / 洞察文件

```yaml
---
description: "1-2 句话描述，用于知识索引"
triggers:
  - "触发加载的场景关键词"
source:
  - "各角色目录/<角色>/经验/xxx.md"
---
```

正文建议包含：
- `## 什么时候需要回溯经验`：什么时候需要回溯到原始经验记录

## 自动沉淀：完成重要工作后主动反思

**不要等用户提醒才沉淀。** 完成以下工作后，AI 应主动提出：

| 场景 | 说明 |
|------|------|
| PRD 多轮修改 | 说明对产品/业务的理解有偏差，偏差本身是宝贵的经验 |
| 方案被否定重做 | 认知校准的最佳时机 |
| 首次跑通流程 | MCP 接入、新工具使用、新 skill 搭建 |
| 反直觉发现 | 数据/现象和预期不符 |
| 用户纠偏 | "不是这样的"——说明 AI 的默认认知和用户的实际情况有 gap |

**具体做法**：工作完成后，主动问自己五个问题：
1. 这次有没有踩坑或发现反直觉的事？→ 经验
2. 能提炼出可复用的 checklist 或模式？→ 技能
3. 有没有值得记住的行为准则？→ 原则
4. 有没有跨场景可泛化的规律？→ 洞察
5. 有没有注意到但没条件验证的疑问？→ 待验证问题

## Comment 机制

当后续发现已有经验失效、需要补充、或与新经历相关时，在该文件末尾添加：

```markdown
## Comments

### <角色> (YYYY-MM-DD)
简要说明（1-2 句），链接到相关文档。
```

comment 是批注和索引，不是正文。深度分析应独立为洞察或技能。

## 联动更新

新建或修改知识文件后：

1. **确保有 description front matter**——这是索引脚本读取的唯一信息源。
2. **跑索引脚本**重建索引：
   ```bash
   python3 知识沉淀/.scripts/build_index.py
   ```
   脚本会自动重建：
   - `知识索引.md` 里每个角色的 `<!-- AUTO:BEGIN role-index:<角色> -->...<!-- AUTO:END -->` 块
   - `各角色目录/<角色>/角色说明.md` 里 `<!-- AUTO:BEGIN role-knowledge:<角色> -->...<!-- AUTO:END -->` 块
3. **不要手工修改 AUTO 块内容**——下次跑脚本会被覆盖。要改描述就改文件自身的 `description` 字段。
4. **检查交叉引用**：技能/原则/洞察 的 `source:` 字段应回链到经验。
5. CI / 协作检查：`python3 .scripts/build_index.py --check` 检测漂移（有未提交的索引变更时退出码 1）。

## 反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|---------|
| 所有经验堆到一个文件 | 检索困难，主题混杂 | 一个事件一个文件，按日期命名 |
| 只写经验不提炼 | 知识停留在"那次踩了个坑" | 写完经验审视能否提炼 |
| 角色专有知识放通用知识 | 污染共享知识库 | 问"其他角色会用到吗？" |
| 人替 AI 写知识 | AI 自己写的对自己更 actionable | 人负责纠偏，AI 负责总结 |
| 沉淀只在犯错时 | 做对的事同样值得记录 | "首次跑通"也是重要经验 |
