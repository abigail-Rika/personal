# 经验沉淀规范

> 当用户说"沉淀一下"/"总结经验"，或 AI 识别到应该沉淀的场景时，按本规范执行。

## 知识分类

| 类别 | 回答的问题 | 存放位置 | 示例 |
|------|-----------|---------|------|
| **experience** | 发生了什么？ | `roles/<role>/experience/` | "PRD 写了三版才过，问题出在没理解审批流程的线下环节" |
| **skill** | 下次怎么操作？ | `roles/<role>/skills/` | "落地页 PRD 的标准写作流程和 checklist" |
| **principle** | 应该/不应该做什么？ | `roles/<role>/principles/` 或 `base/principles/` | "交互方案必须先画状态机，不要直接画页面" |
| **insight** | 为什么会这样？ | `roles/<role>/insights/` 或 `base/insights/` | "PM 给 AI 的需求越模糊，AI 越倾向于做'安全但平庸'的方案" |
| **question** | 待验证的假说 | `roles/<role>/questions.md` | "弹窗的挽留效果是否和弹出时机强相关？需要 A/B 数据验证" |

### 生成关系

```
question（待验证的疑问）
     ↓ 某次实践验证
experience（原始素材）
     ↓ 提炼
skill / principle / insight（可复用知识）
```

## 判断放 role 还是 base

问自己：「如果在另一个工作场景遇到类似情况，这条知识有用吗？」
- 有用 → `base/`（如"理解 ≠ 执行，中间要加 checklist 自检"）
- 只对本角色有意义 → `roles/<role>/`（如"海豚 AI 课的练习题交互有四种状态"）

## 沉淀两步走

### 第一步：先写 experience

记录具体事件——不只是犯错，也包括做对的事。

文件命名：`YYYY-MM-DD-简短标题.md`

最小结构：
```markdown
# 一句话标题

日期: YYYY-MM-DD
角色: product-design / growth / ai-craft

## 背景
发生在什么项目/任务？上下文是什么？

## 经过
做了什么？遇到了什么？用户的反馈是什么？

## 关键收获
这次学到了什么？（1-3 条）

## Triggers（可选）
- "能让 grep 命中的关键词"
```

### 第二步：看能否提炼

从 experience 中抽取可复用的模式：

- **能抽出操作流程吗？** → 写/更新 skill
- **能抽出行为准则吗？** → 写/更新 principle
- **能归纳出跨场景的规律吗？** → 写/更新 insight
- **注意到了但没条件验证？** → 写入 questions.md

只写 experience 不提炼 = 日记。只写 skill 不留 experience = 后人不知道"为什么有这条规则"。两步都要做。

## Skill / Principle / Insight 文件规范

文件开头使用 YAML front matter：

```yaml
---
description: "1-2 句话描述，用于 KNOWLEDGE.md 索引"
triggers:
  - "触发加载的场景关键词"
source:
  - "roles/<role>/experience/xxx.md"
---
```

正文建议包含：
- `## Escalate to experience if`：什么时候需要回溯到原始 experience

## 自动沉淀：完成重要工作后主动反思

**不要等用户提醒才沉淀。** 完成以下工作后，AI 应主动提出：

| 场景 | 说明 |
|------|------|
| PRD 多轮修改 | 说明对产品/业务的理解有偏差，偏差本身是宝贵的 experience |
| 方案被否定重做 | 认知校准的最佳时机 |
| 首次跑通流程 | MCP 接入、新工具使用、新 skill 搭建 |
| 反直觉发现 | 数据/现象和预期不符 |
| 用户纠偏 | "不是这样的"——说明 AI 的默认认知和用户的实际情况有 gap |

**具体做法**：工作完成后，主动问自己五个问题：
1. 这次有没有踩坑或发现反直觉的事？→ experience
2. 能提炼出可复用的 checklist 或模式？→ skill
3. 有没有值得记住的行为准则？→ principle
4. 有没有跨场景可泛化的规律？→ insight
5. 有没有注意到但没条件验证的疑问？→ question

## Comment 机制

当后续发现已有 experience 失效、需要补充、或与新经历相关时，在该文件末尾添加：

```markdown
## Comments

### <角色> (YYYY-MM-DD)
简要说明（1-2 句），链接到相关文档。
```

comment 是批注和索引，不是正文。深度分析应独立为 insight 或 skill。

## 联动更新

新建或修改知识文件后，必须：
1. 更新 `KNOWLEDGE.md` 中对应角色的知识索引
2. 更新 `roles/<role>/ROLE.md` 中的索引条目
3. 检查交叉引用是否完整（experience ↔ skill/principle/insight）

## 反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|---------|
| 所有经验堆到一个文件 | 检索困难，主题混杂 | 一个事件一个文件，按日期命名 |
| 只写 experience 不提炼 | 知识停留在"那次踩了个坑" | 写完 experience 审视能否提炼 |
| 角色专有知识放 base | 污染共享知识库 | 问"其他角色会用到吗？" |
| 人替 AI 写知识 | AI 自己写的对自己更 actionable | 人负责纠偏，AI 负责总结 |
| 沉淀只在犯错时 | 做对的事同样值得记录 | "首次跑通"也是重要 experience |
