# 销售 case 批量钩子识别流程

## 什么时候用

业务场景：拿到一批销售 case 的 user_id（典型规模 10~30 个），要回答"这些 case 用了什么钩子、哪些钩子能成单、成败差异在哪"。例如：

- 给 AI 销售方案找真实参照素材
- 复盘某条投放链路 / 某个销售小组的转化失败原因
- 验证一个"钩子假设"在真实数据里是否成立

不用此流程的场景：
- 用户只给了 1~2 个 case → 直接拉单个 case 复盘（参考 `2026-05-11-真实销售case复盘`）
- 需要做统计显著性 → 样本太小，本流程产出的是定性反差不是定量结论

## 端到端 6 步

### Step 1：明确钩子矩阵 + 软硬属性映射

先把要识别的钩子类型列出来（基于已有方案或本次重新归纳），并标软硬属性。例子（v2 case 库 12 类）：

| 字母 | 钩子名 | 软/硬 |
|---|---|---|
| A | 学情挖掘（教务/老师人设）| 软 |
| B | 班主任承接 | 软 |
| C | 免费送课 | 硬 |
| D | 抢购倒计时 | 硬 |
| F | 价格直推 | 硬 |
| F' | 保障承诺促单（已有意向后）| 软 |
| G | 0 元课激活 + 加微 | 硬 |
| H | 见面会/直播邀约 | 软 |
| I | 老用户升级 | 特殊触发 |
| J | 退费挽留 | 特殊触发 |
| K | 学情反馈 | 软 |
| L | 领课激活提醒 | 硬 |

软硬属性是分类的关键产出——后续主结论几乎都依赖这一层归纳。

### Step 2：批量拉通话录音

用 crm-user-query skill：

```sql
SELECT user_id, ldap, start_at, duration, type, asr_url, note
FROM tutor_call_record
WHERE user_id IN (<15 个 user_id>)
ORDER BY user_id, start_at;
```

筛选条件：
- `duration >= 60`（≥1 分钟，过滤秒挂）
- `asr_url IS NOT NULL`（有转写才能识别钩子）
- `type` 不限（首通/复通/外呼/呼入都要看）

15 user 通常能筛出 30~50 通有效通话。

### Step 3：批量下载 ASR + 抽销售首 8 句

写并发下载脚本（参考 `/tmp/cc_hooks_analysis/download_and_extract.py`）：

```python
import concurrent.futures, urllib.request, json
def fetch(url): return json.loads(urllib.request.urlopen(url).read())
with concurrent.futures.ThreadPoolExecutor(8) as ex:
    rows = list(ex.map(fetch, asr_urls))
```

抽销售首 8 句的逻辑：
- ASR 数据里的角色字段（`role` 或 `speaker`）标 sales / teacher
- 取销售方前 8 个 utterance 的文本
- 这 8 句通常已经能覆盖 "开场 → 自我介绍 → 钩子兑现 → 第一轮追问"

### Step 4：检查 data note 字段——避坑

**关键步骤，不要跳过**。`tutor_call_record.note` 字段经常记录：
- 入口渠道（自然流 banner / 召回 SOP / AI 外呼弹窗）
- 上游事件（用户领了 0 元课 / 试用过期）
- 实际成单链路（电话成单 / 微信成单）

用户给的"成单/未成单 × 人工/AI"标签**经常和 note 不一致**——典型坑：标的"AI 外呼成单"实际入口是 APP 自然流、转化发生在人工微信促单。

校对完 note 再做分类，否则后续对照分析方向是错的。

### Step 5：成单 case 补拉微信原文

通话只能看首接，**成单的临门一脚常在微信里**。对所有成单 case：

```bash
# 走 Chrome osascript + single-chat API，base64 chunk 方案
# 详见 各角色目录/AI工程/经验/2026-05-11-chrome调内部API回传大数据踩坑.md
python3 fetch_wx_v2.py <user_id>
```

拉到的微信原文用来识别：
- 销售如何引导用户做"加微后的关键动作"（试听 / 测评 / 学情诊断）
- 用户的死信号 / 决策权 / 价格敏感点
- 钩子兑现物的实际形态（截图 / 长文 / 语音 / 链接）

未成单的失败 case 不需要全拉，挑 1~2 个最接近成单的拉来做"反差对照"即可。

### Step 6：归类 + 出反差表

按"成单/未成单 × 钩子类型"出表：

| 钩子类型 | 典型话术 | 代表 case | 成单率 | 触达入口 |
|---|---|---|---|---|
| A. 学情挖掘 | "我是 XX 老师，了解一下学习情况" + 5 轮追问 | 176885884 ✅ / 152544830 ❌ | 2/4 = 50% | 落地页直投 |
| G. 0 元激活 | "前两天领了免费课包...加微给您安排" | 845694726 ❌ | 0/1 | AI 外呼弹窗 |

然后看：

- 哪些钩子单独使用能成单 / 哪些 0 成单
- 同一个钩子下成败的"执行差异"是什么（追问深度 / 是否避开价格切入 / 是否退化为 SOP 群发）
- 流量入口和钩子组合的相关性

输出 3~5 条强反差结论，每条挂 2~3 个 case 做证据。

## 产出物

放在项目目录下：
- `真实case素材/v2_钩子分类.md` —— 钩子分类表 + 反差结论
- `真实case素材/case_<user_id>/` —— 单 case 的通话转写 + 微信原文（用于后续深挖）

并把分类结果写回原方案文档（如 v1-初步方案.md §3.4.2.4）。

## 反模式

| 反模式 | 问题 | 正确做法 |
|---|---|---|
| 跳过 Step 4 直接信任用户的口头标签 | 整个对照分析方向错 | 先看 note，发现矛盾立刻和用户对齐 |
| 只看销售首句不看追问深度 | 把"A 钩子失败"归咎于话术，错过真正原因 | 销售首 8 句 + 成单 case 的微信原文 |
| 钩子分类时不标软硬属性 | 12 类钩子的对照表读不出主结论 | Step 1 就把软硬映射定下来 |
| 未成单 case 也全部补拉微信 | 时间成本爆炸 | 只挑 1~2 个最接近成单的做反差 |
| 小样本硬算转化率 | 5 个 case 算出 20% 没有意义 | 出"反差对"而不是百分比 |

## 什么时候需要回溯经验

- 流程在某一步阻塞（如 ASR 下载失败、note 字段缺失）→ 回到 `2026-05-25-AI销售钩子分类-v2case库15用户跑通.md` 看当时的解决方案
- 微信原文回传遇到 6KB title 限制 / Blob 用户手势问题 → 回到 `2026-05-11-chrome调内部API回传大数据踩坑.md` 看 URL hash + base64 方案
- 出反差结论时拿不准"该信用户的标签还是 note"→ 回到经验里"踩坑 1"的判断逻辑
