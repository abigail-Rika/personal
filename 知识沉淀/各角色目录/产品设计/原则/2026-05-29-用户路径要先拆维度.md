# 用户路径要先拆维度再讨论插入点

## 原则

"用户路径"在方案讨论里是个**糅合词**，本身糅杂了至少 5 个独立维度：

| 维度 | 含义 | 决定什么 |
|:-|:-|:-|
| **来源** | 电商 / 直投 / 私域 / 老带新 | 入口文案差异化、进 app 前的认知差异 |
| **设备** | iOS / Android / H5 / 小程序 | 适配范围、UI 版本数、MVP 范围 |
| **支付路径** | 电商支付 / 直投落地页 / 私域销售推链接 | 加微页是否存在、是否前置 |
| **时序** | 购买 → 加微 → 启动 → 前测 → 计划页 → 学 → 首通 | 插入点位置、和销售动作的先后 |
| **激活状态** | 首启动 / 二启动 / 跨设备登录 | 触发逻辑、跨端同步是否支持 |

直接在"路径"层面讨论而不拆维度，会出现两种典型错误：

1. **假共识**：用一个交叉点的共识（如"电商 + 直投在同一个时序点收口"）去代表整条路径已对齐，但其实另外 3 个维度根本没碰过。
2. **漏对齐项**：业务方会按自己关心的维度展开（销售关心时序、电商关心来源 + 设备、增长关心激活状态），如果方案里只展开了一个维度，对齐时会被挨个点名"还没考虑"。

## 判断标准

### 何时触发本原则

- 方案要在用户旅程里**插入新动作**（弹窗、引导、首诊、问卷、卡片）
- 讨论"不同用户路径下方案如何调整"
- 看到"电商 vs 直投""老用户 vs 新用户"这类二元描述被当作完整的路径分析
- 业务方反馈"我们这条路径不是这样的"——通常是另一个维度被忽略了

### 拆维度的标准动作

```text
1. 把"路径"这个词拆成 5 维度表
2. 标注每个维度的 MVP 范围（必做 / 延后 / 不做）
3. 在每个维度内，标注哪些已有共识、哪些是待对齐项
4. 找出维度之间的"交叉判断"——通常这是最容易被漏掉的部分
```

### 容易被忽略的维度

按经验，以下两个维度在方案讨论里**最常被漏掉**：

- **设备维度**：因为大家默认"app 内"，但电商部分渠道（拼多多、抖音商城）可能走 H5 落地页、不进 app
- **激活状态**：因为大家默认"首次启动"，但跨设备登录（手机 A 买、平板 B 学）和二次启动有不同的触发需求

每次拆维度时，**显式问一遍这两个维度**，避免再次漏掉。

## 反向校验

拆完维度、列完每个维度的对齐项之后，反向问一遍：

1. 这条对齐项归属哪个业务方？
2. 这条对齐项的紧急度是什么（卡 MVP 范围 / 卡 MVP 物料 / 一般）？
3. 这条对齐项的状态是什么（已共识 / 待对齐 / 延后处理）？
4. 不同维度的对齐项之间有没有冲突？

四条都能答上来，对齐项才算合格。

## 什么时候需要回溯经验

当你在做"插入点"类的方案讨论时（弹窗、引导、首诊、卡片插哪儿），回看 2026-05-29 档案讨论的经验——纪要 2.1 看似已经把路径定了，展开维度后发现盲区还有 13 条对齐项。

也参考相邻原则 `2026-05-29-指标是产品形态的反向投射.md`——这两条原则常常同时触发：路径泛指 + 指标并列 是方案讨论里掩盖矛盾的两种最常见姿势。
