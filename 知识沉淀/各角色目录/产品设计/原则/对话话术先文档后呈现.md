# 原则：对话话术调试先文档后呈现

## 核心原则

**调对话话术时，必须先建立独立的纯文本脚本文档，调到话术满意了再生成可视化 demo。不要在 HTML/原型/微信样式 demo 里直接改话术。**

## 为什么

可视化呈现会掩盖话术问题。具体的失效机制有 3 个：

1. **视觉光环效应**：微信对话气泡 + 头像 + 时间戳渲染出来后，眼睛会被"挺像那么回事"骗过，话术里的悬浮感被气泡的真实感冲淡。
2. **修改成本拦截**：在 HTML 里改一句话，要去找代码定位、避免破坏样式、可能 token 浪费一大堆——结果就是"差不多就这样吧"。
3. **关注点污染**：可视化 demo 上有 N 个东西在抢注意力（卡片、注解、阶段标签、tab）——评审者很难只盯话术。

## 工作流

### 推荐流程（双层迭代）

```
1. 建对话脚本文档（纯 Markdown）
   - 角色 + 消息分行
   - 用 // 设计意图：xxx 标注关键设计
   - 用 // 待调：xxx 标注疑点
2. 文档里逐句调话术（可能多轮）
   - 评审专注内容
3. 话术冻结后，生成可视化 demo
   - demo 只负责"呈现"，不再改文案
4. 后续修改回到文档，再 sync 到 demo
```

### 文档格式建议

```markdown
**[电话] 19:32 · AI 拨出**

**路**：您好，请问是李明妈妈吗？……
<!-- 设计意图：钩子是服务承诺而不是物料 -->
<!-- 待调：现实里家长大概率会先问"你怎么知道我电话"，需要应对话术 -->

**妈**：哦好的。
<!-- 待调：太顺了，要展示家长更真实的反应 -->
```

- 一句话独立成行 = 调起来直接
- `// 设计意图：` 保留给最终 demo 注解用
- `// 待调：` 标记待讨论疑点，方便快速对齐

## 什么时候需要回溯经验

- 第一次做销售/客服/教练对话脚本时
- 已经做了可视化 demo 但被指出"话术悬浮"时
- 评审会议上大家都在讨论"卡片好看不好看"而不是"话术对不对"时

## 配套：跨 case 对齐

如果脚本有多个用户场景（如 case A/B/C），每个 case 末尾加一个「待讨论核心话术」清单，再在文档底部加「跨 case 通用问题」章节——这样评审者既能聚焦单 case、又能识别共性问题。

## 反模式

| 反模式 | 后果 |
|--------|------|
| 直接在 HTML demo 里写话术 | 话术问题被视觉效果掩盖，评审无效 |
| 文档里只写话术不标 `// 待调` | 评审者不知道哪些是 AI 自己心虚的地方 |
| 一次性写完所有 case 才送审 | 第一个 case 的方向性问题会复制到所有 case |
