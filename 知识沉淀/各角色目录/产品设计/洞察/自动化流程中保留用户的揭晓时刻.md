# 自动化流程中保留用户的"揭晓时刻"

## 规律

当系统替用户完成了决策（自动参与、自动匹配、自动开奖），用户变成被动旁观者，页面变成公告板。

**解法**：把"结果已确定，但展示由用户触发"作为一个独立交互节点。结果不变，但揭晓的动作归用户。

这利用了**刮刮卡 / 盲盒心理**——答案早就印好了，但刮开涂层的动作让人觉得"是我在参与"。

## 来源场景

H5 抽奖页面：用户下单后自动参与所有轮次，开奖也是后台自动按时间触发。如果什么都自动，用户打开页面只能看一堆"你没中奖"的文字列表，毫无体验可言。

设计了「揭晓我的结果」按钮：
- 开奖前：按钮显示"等待开奖"（置灰）
- 开奖后：按钮变为"揭晓我的结果"（高亮 + 呼吸灯）
- 点击后：翻转动画 → 展示中奖/未中奖

用户离开一段时间回来，会发现多张卡片等待揭晓 → 连续拆盲盒体验 → 增加停留和复访。

## 适用场景

| 场景 | 自动化部分 | 可保留的"揭晓"动作 |
|------|-----------|-------------------|
| 抽奖 | 自动参与 + 自动开奖 | 揭晓我的中奖结果 |
| 匹配/推荐 | 系统自动匹配老师/课程 | 查看我的专属匹配结果 |
| 积分兑换 | 到期自动兑换 | 查看我获得了什么 |
| 学习报告 | 系统自动生成 | 打开我的学习报告 |
| 排行榜 | 自动计算排名 | 揭晓我的本周排名 |

## 设计要点

1. **揭晓按钮需要视觉提示**（呼吸灯、红点、数字角标），让用户知道"有东西等你看"
2. **积攒过多未查看时提供批量揭晓**，避免操作疲劳（如超过 3 轮未查看 → 提供"一键查看所有"）
3. **揭晓动画要短**（0.3-0.5s 翻转即可），不要让用户每次等太久
4. **未揭晓不等于未参与**——后台该做的逻辑照常运行，揭晓只影响前端展示

## 什么时候需要回溯经验

当设计"用户被动等待结果"的场景时，可以回溯这条洞察，考虑是否适合加入揭晓动作。
