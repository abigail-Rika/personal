# PRD 完整性检查要走角色动线，而非功能清单

## 核心观点

PRD 常见的完整性检查方式是"功能点是否全覆盖"：登录有没有、抽奖有没有、开奖有没有……但这样检查容易遗漏**角色之间的交接环节**。

更靠谱的检查方式是：**沿着每个角色的操作动线走一遍，看是否闭环。**

## 来源场景

H5 抽奖页面 PRD 中：
- §1.3 写了"销售在微信群/私聊中群发 H5 页面链接"
- §5.3 写了"后台不自动生成 H5 页面，前端独立开发"
- 但**运营从哪获取这个 H5 链接**？PRD 没有任何描述

功能层面没有遗漏（H5 页面、后台配置、抽奖逻辑都写了），但**运营的操作动线断了**：配完抽奖 → ？ → 销售拿到链接。中间这个"？"就是交接断点。

## 为什么会遗漏

写 PRD 时，PM 自然地站在"用户视角"和"系统视角"交替思考，但容易遗漏"运营/内部角色视角"。因为：
- 用户流程是 PRD 的主线，PM 会仔细走
- 系统逻辑（接口、数据流）有技术评审兜底
- **运营操作流程** 既不是用户流程，也不是技术细节，处于两者的夹缝中

## 检查方法

写完 PRD 后，列出所有涉及的角色（不只是用户），逐个走动线：

| 角色 | 动线示例 | 要检查的问题 |
|------|---------|-------------|
| 用户 | 打开链接 → 登录 → 看奖品 → 等开奖 → 看结果 | 每步是否都有状态和反馈？ |
| 运营 | 配置轮次 → 获取链接 → 给销售 → 活动结束 → 查看数据 | 每步在哪个系统操作？入口在哪？ |
| 销售 | 拿到链接 → 群发 → 用户有问题怎么答 | 链接从谁手里拿？有 FAQ 吗？ |
| 研发 | 看 PRD → 开发 → 联调 → 验收 | 接口定义清楚吗？验收标准可执行吗？ |

**关键检查点**：角色 A 的动线输出，是否是角色 B 的动线输入？如果断了，就是交接缺口。

## 什么时候需要回溯

- Review PRD 时，作为检查维度之一
- PRD 涉及后台操作 + 前端页面 + 多角色协作时，尤其要走运营动线
