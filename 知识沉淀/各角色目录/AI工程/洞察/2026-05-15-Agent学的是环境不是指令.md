# Agent 学的是环境，不是指令

> Ryan Lopopolo（OpenAI Symphony 团队）原话：
>
> 「Agent 会复制 repo 里已有的模式，包括坏模式。只要有一个文件写得差，一周之内 agent 会把这个坏模式复制得到处都是。」
>
> 「现有代码库质量比 prompt 更重要。Agent 学的是环境，不只是指令。」

## 核心判断

Agent 的实际行为 = `f(指令, 环境)`，且**环境的权重远高于指令**。

环境包括但不限于：
- 它能看到的代码 / 文档 / 历史输出（few-shot examples 中的 case）
- 它能调用的工具（tool definition 的措辞和示例）
- 它读到的同类任务的"参考样本"（即便没显式 few-shot，agent 也会从上下文里推测"这家公司的风格"）
- 它接手的半成品（前面 agent 留下的代码 / 对话 / 标注）

**这意味着**：你的 system prompt 写得再 RFC 2119、再清晰，只要环境里塞了 5 个坏 case，agent 的实际产出会强烈对齐那 5 个坏 case，而不是你写的规则。

## 同型迁移：四个场景下"环境 > 指令"的表现

| 场景 | "指令"指什么 | "环境"指什么 | 表现 |
|---|---|---|---|
| **AI 写代码** | system prompt + AGENTS.md | 现有 codebase 的写法、test 风格、commit message 风格 | 写 prompt 强调"要写 unit test"没用——repo 里没有 test 文件，新 agent 也不会写 |
| **AI 销售对话** | 话术 prompt | case 库里的真实成单/失败对话、SOP 模板的语气、客服历史回复 | prompt 写"不要长聊轰炸"没用——case 库里全是长聊轰炸成单的样本，agent 会复制 |
| **AI 学情诊断** | 诊断 prompt | 老师过往诊断报告的样本、家长反馈记录、教材结构 | prompt 写"诊断要具体"没用——参考样本全是"知识掌握不牢、需要加强练习"这种空话，新报告也是空话 |
| **AI 标注 / 整理** | 标注规则 prompt | 之前标注的样本（不管是 AI 标的还是人标的） | prompt 改了，但旧标注还在数据集里，新标注会向旧标注靠拢 |

**共同模式**：**Agent 不是按规则推理的，是按 pattern matching 工作的**。你给的"规则"只是众多 pattern 之一，且权重远小于"看起来像什么"的 pattern。

## 推论 1：失败时第一反应不是改 prompt，是查环境

> Ryan：「当 agent 失败时，大多数人的第一反应是『我是不是应该换个 prompt？』我们问的是：『环境里缺了什么能力、上下文或结构？』」

具体差异：

| 失败现象 | 错误反应（prompt 派） | 正确反应（环境派） |
|---|---|---|
| AI 销售开场啰嗦 | 改 prompt "开场要简洁，≤30 字" | 看 case 库里的样本是不是都很长 → 如果是，先清/重标几个简洁样本 |
| AI 写的 PR 缺测试 | 改 prompt "必须写测试" | 看 repo 里测试覆盖率多少 → 如果低，先补几个标杆测试 |
| AI 学情诊断空泛 | 改 prompt "诊断要具体到题目" | 看参考报告是不是都空泛 → 是的话先人工写 3-5 份高质量标杆报告塞进环境 |
| AI 回复家长拒绝时硬磕 | 改 prompt "遇到拒绝要止损" | 看历史会话里"拒绝→止损"的样本有几个 → 大概率为 0，需要补 |

**判据**：你已经第 3 次改 prompt 了，问题没明显变好 → 大概率不是 prompt 的问题，是环境的问题。

## 推论 2：坏样本扩散比好样本生长快得多

> Ryan：「对 agent 来说，删除坏 pattern 比添加好 pattern 更难。它不会自然判断『这个 pattern 不好』，它倾向于复制环境里已经存在的东西。」

**对应到我们的工作**：

- AI 销售 case 库里如果混进 1-2 个长聊轰炸成单的 case，未来 agent 会学这个路径——哪怕这个 case 只是侥幸成单、不可复制
- AI 标注的数据里如果有错误标注没被清理，新一轮 AI 标注会向错误对齐
- 知识沉淀目录里如果留下过时/错误的原则，未来 agent 会优先匹配它

**治理对应**：

1. **入库审核 > 入库后修正**——case 库 / 标注 / 样本进库前要审，进库后修很难
2. **错误样本要主动删，不要 fix 注释**——加一行"这个 case 不好"的注释，agent 不一定看；直接删干净
3. **标杆样本要数量多 + 一致性强**——单个高质量样本顶不住 10 个平庸样本的统计权重

## 推论 3：现有产物的质量决定 agent 上限

如果我让 agent 接着写一份已经写得很烂的 PRD，它会继续写烂——它的"风格基线"就是这份 PRD。

**操作含义**：

- 让 agent 接手任务前，先**人工/单独 agent 修一遍"环境样本"**，再让接手 agent 开工
- 不要在垃圾代码上让 agent"重构"——大概率重构出来还是垃圾。先人工/精细 agent 写一个干净的标杆，agent 再扩展
- AI 销售场景：**给 agent 跑之前先重写 5-10 个"理想对话样本"作为环境基线**，比反复调 prompt 杠杆大得多

## 我们工作里的具体应用

| 场景 | 应用 |
|---|---|
| **AI 销售 0 转体 PRD** | 与其无限调对话 prompt，不如先精修 5-10 个"理想首通对话样本"塞进环境（理想链路-demo文字稿.md 就是干这个的）|
| **case 库治理** | 已有 case 库要做一次"环境审查"——失败 case 用来训练止损，但**成功 case 里如果有"侥幸成单的坏路径"，要标红或剔除**，否则 agent 会学坏路径 |
| **知识沉淀** | 错误/过时的原则要主动删，不要靠"标过时"——agent 不可靠地区分 |
| **PRD 写法** | 团队里如果有一份 PRD 写得很好（如 ROI 弹性测算那份），把它显式标成"标杆 PRD"放在显眼位置，让 agent 优先匹配这个风格 |
| **agent 接手任务** | 让 agent 接手前，先人工 review 它会读到的 5 个相关文件，看有没有"坏样本"——有就先清 |

## 反方向边界（不要矫枉过正）

这条不否认 prompt / 指令的价值，它说的是**权重排序**：环境 > 指令。

- 环境对了，没指令也能拿到 70 分
- 环境不对，再好的指令也只能 50 分
- 环境 + 好指令 = 90 分

所以正确做法是：**先治环境，再调指令**，不是只治环境不写指令。

## 什么时候需要回溯

- prompt 调了 3 次以上还没明显改善时
- AI 销售 / AI 诊断 / AI 标注质量上不去时
- 接手一份"前人留下的烂摊子"想让 agent 重构时
- 团队讨论"为什么换了模型也没变好"时
- 设计新的 case 库 / 样本库 / 知识库时（**入库审核机制要在这条原则下设计**）
