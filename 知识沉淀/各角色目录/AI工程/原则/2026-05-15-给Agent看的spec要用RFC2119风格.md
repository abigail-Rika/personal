# 给 Agent 看的 spec 要用 RFC 2119 风格

> 给人看的 PRD 讲故事、传达 why；给 agent 看的 spec 必须告诉它"什么是对、什么是错"，可以被自动校验。两套文档物理上可以是一份，但表述风格必须切换。

## 准则

任何要被 agent 反复执行的规则（对话话术、判断逻辑、状态机、生成约束），文档表述 MUST 满足以下全部：

1. **每条规则有唯一编号**（如 `REQ-5.3.1.2`），后续争论和违规追溯都引用编号
2. **用 RFC 2119 语气**：`MUST` / `MUST NOT` / `SHOULD` / `SHOULD NOT` / `MAY`，禁止"尽量"、"原则上"、"通常"、"灵活处理"
3. **可枚举的判据强制枚举**，不要用"等"留口子；如果真的需要 fallback，显式写一条 `default` 分支
4. **冲突时的优先级显式声明**（如「同时命中 A 和 B 时，MUST 按 B 处理」）
5. **必须有反例**（❌ 示例），且每个反例 MUST 标注违反了哪条编号
6. **必须有正例**（✅ 示例），且 SHOULD 标注命中了哪条编号

## 判据：fresh agent 测试

> spec 写得够清楚 ⇔ fresh agent（开新窗口、零上下文、只看这份 spec）能复现你期望的行为。

如果做不到，**spec 不够清楚**，不是 agent 不够聪明。

具体操作（Ralph Loop 简化版）：

1. 把 spec 单独丢到新窗口
2. 让 fresh agent 按 spec 处理一个真实输入（如一段真实用户对话）
3. 对比 fresh agent 的判定 / 输出 vs 你心里的标准答案
4. 差异点 = spec 漏的地方
   - fresh agent 判错 → 描述有歧义，需要补判据
   - fresh agent 判不出来（"无法判断"） → 漏了枚举或漏了优先级
   - fresh agent 判对了但理由和你不一样 → 推理路径不唯一，需要补排序

跑 2-3 个真实输入，spec 会自己长出来。

## 风格对照

### 反模式：给人看的 PRD 风格

| 信号类型 | 具体表现 | AI 应对 |
|---|---|---|
| 主动信号 | 问价格/购买细节、问后续安排、替孩子做计划 | 跳过剩余流程，直接引导购买 |
| 隐性信号 | 认可问题方向、主动补充孩子情况 | 把体验课解释为低成本学习采样 |
| 无信号 | 家长回复少、只给基础信息、不追问 | 不强推 |

**问题**：

- "主动信号"边界模糊——"主动补充孩子情况"算哪种？
- "跳过剩余流程"具体跳到哪？不明确
- "不强推"边界在哪？发 1 条还是 5 条算强推？
- 冲突未处理：上一轮 IMPLICIT、这一轮变 NONE 怎么办？

### 正模式：给 agent 看的 spec 风格

**REQ-5.3.1 购买信号识别与应对**

5.3.1.1 AI MUST 在每次家长回复后做一次购买信号分类，结果有且仅有一个：`MAIN` / `IMPLICIT` / `NONE`。

5.3.1.2 `MAIN` 的判据 —— 以下任一命中即为 `MAIN`：
- a) 明确询问价格（含"多少钱"、"几块"、"贵吗"等）
- b) 明确询问报名 / 支付方式
- c) 明确询问上课安排
- d) 家长替孩子做出行动安排

5.3.1.3 `IMPLICIT` 的判据 —— 5.3.1.2 全部未命中，且以下任一命中：
- a) 认可 AI 提出的问题方向
- b) 未被追问时主动补充孩子情况
- c) 追问方法类问题

5.3.1.4 `NONE` 的判据：以上均不命中。

5.3.1.5 判为 `MAIN` 后，AI MUST 在下一轮进入"引导购买"流程，MUST NOT 继续追问延迟成交。

5.3.1.6 判为 `NONE` 后，AI MUST 用一条 ≤ 60 字总结收尾，MUST NOT 主动提购买。

5.3.1.7 **单调升级原则**：会话内一旦判为 `MAIN`，后续轮次即便家长回归冷淡，AI MUST 继续按 `MAIN` 推进，直到家长**显式**说"不买"或会话超时。

❌ 反例：判定为 `MAIN` 后又问"再了解一下您家孩子最近作业情况" → 违反 5.3.1.5
✅ 正例：判定为 `MAIN` 后下一条直接报价 + 优惠 + 适配推荐 → 命中 5.3.1.5

**好处**：

- 任何一条 AI 输出可以被自动校验对错
- 出错时能精确指着规则编号说"违反 5.3.1.5"
- 5.3.1.7 这种 corner case 在表格风格下完全不会被想到，spec 化时被逼出来

## 什么时候必须用，什么时候不必

| 情况 | 是否必须 RFC 2119 风格 |
|---|---|
| 对话话术 / 状态机 / 判断规则（AI 反复执行） | **必须** |
| 数据口径 / 计算公式 / 实验设计 | **必须** |
| 给人看的 PRD 故事 / 背景 / 为什么 | **不必**——讲故事的风格更易读 |
| 一次性的方案讨论文档 | **不必**——浪费时间 |
| 调研 / 复盘 | **不必** |

**最佳实践**：一份 PRD 内部分两层。前半部分给人看（讲清楚 why、机会、风险、方案大方向），后半部分给 agent 看（具体规则用 REQ-编号 + RFC 2119）。两层互相引用：「具体执行细则见 §5.3.1」。

## 反模式检查

写完 agent-facing 段落后，自检：

- [ ] 出现"尽量 / 视情况 / 灵活 / 必要时" → 倒回去拆成 `MUST` / `SHOULD` / `MAY`
- [ ] 出现"等"留口子 → 改成枚举或加 default 分支
- [ ] 同一规则两个判据可能同时命中却没写优先级 → 加冲突处理条款
- [ ] 没有 ❌ 反例 → 至少补 1 个
- [ ] 没有编号 → 加编号
- [ ] 描述了"做什么"但没描述"不能做什么"（negative space 缺失） → 补 `MUST NOT`

## 为什么这条要立成原则

2026-05-15 阅读 OpenAI Symphony SPEC.md 时发现：他们的 spec 是给 6 种语言的 fresh agent 同时实现的，**精确度的唯一办法就是 RFC 2119 + 编号 + 反正例 + 冲突优先级**。

把这套搬到 AI 销售 PRD 上做了一次小范围验证（购买意愿判断 7 条规则 + 加微钩子约束 6 条），发现：

- 同一段内容原 PRD 表格风格 ~5 行，spec 风格膨胀到 ~25 行
- 但 spec 风格强制暴露了 3 个原 PRD 没考虑的 corner case（单调升级、KNOWN+CHURNED 冲突、红线词清单）
- **膨胀的 5 倍体量换来的是"agent 跑 1000 次的方差从大到小"**——这是结构性收益

**核心判断**：模糊的 PRD = 把"对错判断"的决策权延迟到每一次 agent 运行时，方差大且无法追溯。RFC 2119 风格 spec = 把"对错判断"提前到一次性的写作行为，agent 运行时只做执行不做判断。
