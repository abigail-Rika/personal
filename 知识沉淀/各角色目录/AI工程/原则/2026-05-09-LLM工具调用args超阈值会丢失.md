# LLM 工具调用 args 超阈值会丢失

## 原则

**LLM 在生成 inline 工具调用时，args 字段值如果是大字符串（实测阈值约 1k–2k 字符），整个 args 字段会丢失或截断。** 不要在内容长度未知/超阈值的情况下尝试 inline 提交，必须先评估长度，超阈值就改路径。

## 现象识别

典型错误信息：

```
Tool execution error. Expected ',' or '}' after property value in JSON at position N
```

`position N` 通常在 args 开头不远处（如 position 69、150 等）。这说明 LLM 实际生成的 args JSON 在那个位置出现了非法字符或截断，**不是工具的参数校验失败，是 args 字段根本没生成完整**。

实测数据点（Cursor + MCP 环境，2026-05）：

| content 长度 | 是否成功 |
|-------------|---------|
| ~50 字符 | ✅ |
| ~200 字符 | ✅ |
| ~1.5k 字符 | 未测，估计可行 |
| ~17k 字符 | ❌ 每次 args 整体丢失 |

阈值大约在 1k–2k 之间（具体值随模型/环境变化）。

## 判断逻辑

```
我要调用一个 MCP 工具，args 里有一个内容字段（content / body / text）
  ↓
内容字段长度估计是多少？
  ├── < 1k 字符 → 可以 inline 提交
  ├── 1k–2k 字符 → 谨慎，先在临时对象试一次；不行就走脚本
  └── > 2k 字符 → 直接走脚本路径或人工粘贴
```

## 超阈值的正确路径

### 路径 A：人工粘贴（最稳）

适用于「用户在前端有编辑权限」的场景（Confluence、Notion、Google Docs 等）。

1. AI 把要同步的内容写到本地 `.tmp-sync/<file>.md`
2. 告诉用户：路径 + 操作步骤（打开哪个页面、删掉哪段、粘哪段）
3. 用户手工完成

代价：用户多花 1–2 分钟。
收益：100% 不会出错、不会覆盖错位置。

### 路径 B：脚本中转（自动化）

适用于「需要批量同步」或「用户没有 UI 编辑权限」的场景。

1. 内容写到本地文件
2. 写一个 Python/Node 脚本，从文件读内容，调 API（不通过 LLM args）
3. 在 Shell 里运行脚本

注意：脚本本身的 LLM 输出也有长度限制，但脚本只需要写一次（典型 50 行以内），不需要在 args 里塞大字符串。

### 路径 C（不推荐）：分块提交

把内容分成 < 1k 字符的多块，多次调 update。

问题：
- update 类工具大多是「整体覆盖」语义，分块会导致每次都覆盖前一块
- 即使有 append 接口，也容易因为顺序错乱导致内容损坏

## 反模式

| 反模式 | 后果 |
|--------|------|
| 不评估长度直接 inline 提交 | 多次 args 丢失，每次都要等错误返回，浪费时间 |
| 失败了多试几次（"也许这次能成"） | LLM 输出 token 限制是稳定的，重试同样大小 args 不会成功 |
| 失败后改写 short 字符串去"探探路" | 见 `2026-05-09-写入工具不要在生产对象上做test.md`——会覆盖生产数据 |
| 默认用户没有手工能力 | 用户能在 UI 编辑的场景，手工 30 秒就能完成；不要为了"自动化"反而把简单事搞砸 |

## 自检清单

inline 调用 MCP 写入工具前问自己：

- [ ] 我要传的 content 有多长？（数一下大概字符数）
- [ ] 这个长度在历史经验中能成功传过去吗？
- [ ] 如果 args 失败，目标对象会处于什么状态？（如果会变成损坏状态，更要谨慎）
- [ ] 是不是更该让用户手工粘贴？

## 与现有原则的关系

- `2026-05-09-写入工具不要在生产对象上做test.md` 解决「**怎么试**」
- 本原则解决「**能不能 inline 提交**」（评估长度、选路径）
- 两者一起回答：要往生产系统写大内容时，应该走什么路径
