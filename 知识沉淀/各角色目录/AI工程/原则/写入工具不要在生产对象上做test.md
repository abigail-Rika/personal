# 写入工具不要在生产对象上做 test 调用

## 原则

**MCP 写入类工具（update / write / send / create）没有 dry-run，绝不在生产对象上做"测试是否能传参"或"探索 API 行为"类的调用。** 任何这类调用都会真实覆盖/创建/发送数据。

## 判断逻辑

```
我想验证某个 MCP 写入工具的参数格式 / API 行为 / 是否能调通
  ↓
我打算调用它的目标对象是不是用户在用的生产数据？
  ├── 是 → 停。换一个新建的临时对象（test sandbox）
  └── 否 → 可以测
```

## 为什么

1. **写入类工具没有 transaction**：`update_page("hello")` 调用瞬间，目标页面就被覆盖成 "hello"。不像数据库的 `BEGIN ... ROLLBACK`，没有撤销空间。
2. **占位字符串也是真实覆盖**：即使 content 是 `"test"`、`"hello"` 这种明显是测试的内容，用户在前端看到的也是真实的 "test"——不会因为字符串"看起来像测试"就不生效。
3. **错觉：调用成功 = 行为正确**。`update_page` 返回 `{"message": "Page updated successfully"}` 是正确的——它确实更新成功了。但更新成的内容是测试垃圾，不是想要的内容。**调用成功 ≠ 业务正确**。
4. **回滚成本不对等**：你为了节省 30 秒的"用户去 UI 手工恢复"时间，可能让自己花 10 分钟试错、用户花 5 分钟看到错误页面、解释半天发生了什么。

## 正确做法

### 验证 MCP 写入工具的步骤

```
1. 调用 create_xxx 新建一个临时对象（如 __test_sandbox__ 页面）
2. 在临时对象上做 update / 各种参数测试
3. 验证完，调用 delete_xxx 销毁临时对象
4. 真正同步到目标对象——这一步只在已经把内容准备好、不需要再"试"的时候做
```

### 关键问句（写入前自问）

- **如果这次调用真的生效了，会不会破坏数据？** → 会 → 不能在这个对象上调
- **我现在是为了"试"还是为了"做"？** → 试 → 换 sandbox

## 泛化

这条原则适用于所有有副作用的写入操作：

| 工具类型 | 典型工具 | 测试沙箱方式 |
|---------|---------|-------------|
| 文档系统 | Confluence update_page、Notion update_database_row | create 一个临时页面/行 |
| 数据库 | DB update / insert | 用 transaction + ROLLBACK；或新建临时表/行 |
| 消息 | 企微/Slack send_message | 发到只有自己的 channel |
| 邮件 | send_email | 发给自己 |
| 日历 | create_event | 标题加 `[TEST]` 前缀，建在专门的测试日历 |
| 代码仓 | create_pr / push | 在 fork 仓库 / 测试分支 |

## 反模式

| 反模式 | 后果 |
|--------|------|
| "用 short 字符串测试 args 是否能传过去" | 把生产页面覆盖成 short 字符串 |
| "先 update 一下看看 API 反应" | 即使 API 反应正常，目标已经被改了 |
| "反正等会儿就改回来" | 改回来需要再一次成功调用，可能再次失败 |
| "用户能从 UI 看到，让用户手工恢复" | 是兜底方案，不是预期方案；不该靠用户给自己擦屁股 |

## 与现有原则的关系

- `外部系统写入需要明确授权.md` 解决「**该不该写**」（用户授权）
- 本原则解决「**怎么试着写**」（不能在生产对象上试）
- 两者都是写入操作前必过的关卡
