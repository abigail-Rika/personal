# 协作反模式：工具盲信与过度复杂化

日期: 2026-04-01
角色: AI工程

## 背景

两个场景暴露了 AI 协作中的反模式：
1. 回顾「流量承接分析」的历史对话时，Glob 工具对中文路径返回 0 结果，AI 直接下结论"目录是空的"，被用户截图打脸
2. 在原始分析协作中，用户说"画个示意图"，AI 做了一张复杂的生命周期循环图，用户纠正后改为简单的并排漏斗对比

原始对话见 `backups/agent-chats/2026-03-23` 的 `410cf5e7`。

## 经过

### 反模式 1：工具返回空结果时盲信

```
Glob("**/*", target_directory="...personal/历史聊天")  → 0 files
Glob("**/*", target_directory="...personal/backups")    → 0 files
```

Glob 返回 0 结果后，直接说"目录是空的"。用户截图指出不对后，改用 Shell 的 `find` 命令立刻找到大量文件。

根因：Glob 工具对包含中文字符的路径（`历史聊天`）处理有问题，但 AI 没有意识到工具本身可能有局限，也没有用第二种方式交叉验证。

### 反模式 2：倾向于过度复杂化

用户说"画个流程图或者示意图"，AI 的第一反应是做一张包含 4 层生命周期、回流循环箭头、3 种承接方式色块的复杂 HTML 页面。用户看完后说：

> "其实我是想分流量类型去看用户旅程，以及漏斗转率"

整个可视化重做。后续用户的每次反馈都是在做减法："析出率不用看具体点位""单位经济模块先不加了""进入 app 率就不要了"。

### 反模式 3：长对话没有及时分段

原始分析对话做到 11000 行时用户主动问"上下文会不会太多了"。其实在数据框架搭好之后（约 1/3 处）就应该建议切新对话。协作协议里有"长对话及时分段"这一条，但没主动执行。

### 反模式 4：多份关联文档没有标注 Source of Truth

分析文档和 Rule 文件（`增长-流量分级.mdc`）的分级定义出现了不一致——前测析出在分析文档是 B 级，在 Rule 里是 A 级。两份文件写在不同时间点，没有标明"谁以谁为准"。

## 关键收获

1. **工具结果为空 ≠ 事实为空**：尤其是中文路径、深层嵌套、特殊字符场景，一个工具返回空时必须用第二种方式（`ls`/`find`/`Shell`）交叉验证。这应该成为肌肉记忆。
2. **从最简版本开始，逐步加复杂度**：AI 的默认行为是"尽可能全面"，但用户通常想要的是最小可用版本。先问"你想看什么形态"，做最简版，用户确认后再迭代。
3. **确认输出形态再动手**："画个图"太模糊——是并排对比还是流程图？是给自己看还是给领导汇报？动手前多问一句，省掉一次完整返工。
4. **分段执行协作协议**：协作协议里的条目不只是文字——"长对话及时分段"需要在对话过程中主动判断和执行，而不是等用户提醒。
5. **多文档产出必须标注依赖关系**：当分析文档和 Rule 文件同时存在时，明确哪个是 Source of Truth，另一个是派生。

### 反模式 5：归档位置默认错误

用户说"归档吧"，AI 默认放到了 `aries/团队-增长/项目归档/`（团队空间），用户纠正"不要归档到 aries 啊，我说归档的时候是指放到 personal 里"。

根因：没搞清楚用户的默认 context。用户的个人工作产出默认归 personal 空间，只有明确说"放到团队空间"时才放 aries。

## Triggers

- Glob 返回空、搜索无结果、工具失效
- 中文路径、特殊字符路径
- 交叉验证、二次确认
- 过度复杂化、做减法
- 输出形态确认、需求对齐
- 长对话、上下文膨胀、分段
- Source of Truth、多文档一致性
- 归档、存放位置
