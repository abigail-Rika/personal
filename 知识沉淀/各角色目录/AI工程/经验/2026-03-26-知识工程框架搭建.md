# 首次搭建知识工程框架

日期: 2026-03-26
角色: AI工程

## 背景

用户读到 stonepage 的《Agent 知识工程实践》文章后，要求基于文章思路搭建一套适配当前 workspace 的知识框架。当前 workspace 是 PM（产品经理）与 AI 在 Cursor IDE 中协作，非典型的 Coding Agent 场景。

## 经过

### 做了什么

1. 用 Playwright MCP 抓取知乎文章全文（知乎反爬严格，普通 fetch 403），归档到 `tech/2026-03-26-agent-知识工程实践.md`
2. 盘点现有体系：7 个 Cursor Rules、`知识沉淀/` 目录（skills 评估 + 2 篇 tech 文章）、协作协议
3. 识别关键适配点：Cursor rules 系统 vs AGENTS.md、PM 工作角色 vs 开发角色、always/requestable 加载 vs grep 检索
4. 搭建框架：KNOWLEDGE.md（总索引）、沉淀规范、3 个角色（product-design / growth / ai-craft）、目录结构
5. 将协作协议与知识框架对接，在 `协作协议.mdc` 中增加"知识沉淀"章节

### 关键设计决策

- **不照搬原文的 AGENTS.md 模式**：Cursor 已有 rules 系统管理"不变的规则"，知识库专注于"生长的经验"，两者互补而非替代
- **角色划分按用户工作领域**：product-design / growth / ai-craft，而非按技术栈
- **保留已有结构**：skills 评估体系、tech 文章归档原地不动，在新框架中建立索引指向

## 关键收获

1. **知识框架要适配加载机制**：原文假设的加载方式是"AGENTS.md 常驻 + grep 按需"，Cursor 的加载方式是"always_applied rules 常驻 + agent_requestable 按需"。框架设计必须贴合实际的加载能力，否则知识写了也读不到
2. **空框架不是浪费**：大部分角色目录是空的，但目录结构本身就是"沉淀的邀请"——看到有地方可以放，才会想到要放
3. **第一条 experience 最难写**：框架再完美，如果没人往里填内容就是摆设。用"搭建过程本身作为第一条 experience"来破冰
