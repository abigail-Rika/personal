# 知识库总索引

> 本文件是 AI 助手的知识加载入口。每次协作开始前，AI 应通读本文件确认角色和可用知识。

## 设计理念

**Agent 不是菜，他只是不知道。**

这套知识体系的目的是让 AI 助手在持续协作中积累上下文知识，从"每次从零开始的聪明新人"变成"越用越懂你的协作伙伴"。

核心原则：
- 知识由 AI 自己写，人负责纠偏和追问"为什么"
- 先记再整理——先让知识流动起来，体系在记的过程中自然生长
- 简单性是持续运转的关键——目录结构 + Markdown，grep 就能搜索

- 原则：
  - `各角色目录/AI工程/原则/2026-04-01-工具结果为空时必须交叉验证.md` — AI 工具返回空结果时，必须用第二种方式验证，不能直接下结论。尤其注意中文路径、深层嵌套等工具盲区。
  - `各角色目录/AI工程/原则/2026-04-09-外部系统写入需要明确授权.md` — 往外部系统（Notion、日历、邮件等）写入数据是高权限操作，必须有用户明确指示才能执行。默认用最轻量的方式满足需求。
  - `各角色目录/AI工程/原则/2026-05-09-LLM工具调用args超阈值会丢失.md` — LLM 在 inline 生成工具调用参数时，长字符串（实测约 1k–2k 字符以上）作为 args 字段值时整个 args 会丢失，触发 'Expected , or } at position N' 类 JSON 解析错误。这是模型输出 token 的硬限制，不是工具问题。超阈值的内容同步必须改走文件 + 脚本路径或人工粘贴，不能在生产对象上反复试错。
  - `各角色目录/AI工程/原则/2026-05-09-写入工具不要在生产对象上做test.md` — MCP 写入类工具（update_page、update_record、send_message 等）大多没有 dry-run，任何调用都是直接覆盖。绝不能在生产对象上做'测试一下能不能传 args'之类的 test 调用——即使 content 是占位字符串，也会真实覆盖目标。验证应该在新建的临时沙箱对象上做。
  - `各角色目录/AI工程/原则/2026-05-15-给Agent看的spec要用RFC2119风格.md` — 给 Agent 看的 spec / 文档必须用 RFC 2119 风格（MUST/SHOULD/MAY + 编号 + 反正例），不能依赖人类默契。判据：fresh agent 只看这份 spec 能不能复现你期望的行为。
  - `各角色目录/AI工程/原则/2026-05-25-重要协作结束前必须做沉淀判断.md` — 知识系统要形成完整运行闭环：开工前先读旧知，执行中按旧知约束行动，收尾时显式判断是否需要沉淀新知，最后更新索引。只写不读、只读不沉淀，都会让知识体系失效。
  - `各角色目录/AI工程/原则/2026-08-13-CLI程序不走系统代理需显式设置.md` — 命令行程序（Rust/reqwest 等）默认不读 macOS 系统代理设置，走网络前需显式设 HTTP_PROXY/HTTPS_PROXY；判断地区限制前先确认本机代理出口 IP。
  - `各角色目录/AI工程/原则/2026-08-15-打开本地文件先确认路径与工作区.md` — 打开本地文件前，必须先确认用户给出的精确路径存在且当前编辑器处于对应工作区，再选择侧边栏、快速切换器或系统打开等最轻操作路径。

## 知识加载策略

### 与 Cursor Rules 的关系

```
┌─────────────────────────────────┐
│  Cursor Rules (.cursor/rules/)  │  ← 系统级加载，由 Cursor 管理
│  ┌───────────────────────────┐  │
│  │ always_applied            │  │  协作协议.mdc（常驻）
│  ├───────────────────────────┤  │
│  │ agent_requestable         │  │  产品上下文、UI规范、交互原则...
│  └───────────────────────────┘  │  （AI 判断相关时主动加载）
└─────────────────────────────────┘
              ↕ 互补
┌─────────────────────────────────┐
│  知识沉淀/ (本知识库)            │  ← 协作级知识，在对话中按需读取
│  ┌───────────────────────────┐  │
│  │ 知识索引.md（本文件）      │  │  索引入口，知道有什么
│  ├───────────────────────────┤  │
│  │ 各角色目录/<角色>/角色说明 │  │  角色描述 + 细分索引
│  ├───────────────────────────┤  │
│  │ 经验 / 技能 / 原则 / ...  │  │  具体知识，通过索引命中后加载
│  └───────────────────────────┘  │
└─────────────────────────────────┘
```

**Cursor Rules 存"不变的规则"**（产品上下文、UI 规范、交互原则）——这些由人主动维护，变更频率低。

**知识沉淀/ 存"生长的经验"**（踩坑记录、协作模式、复盘洞察）——这些在每次协作中自然产生，由 AI 主动沉淀。

### 加载时机

| 层级 | 内容 | 时机 |
|------|------|------|
| **常驻** | `协作协议.mdc` | 每次对话自动加载 |
| **任务启动** | 本文件 `知识索引.md` | 复杂任务开始时，快速扫描可用知识 |
| **按需** | `各角色目录/<角色>/角色说明.md` → 具体经验/技能 | 命中关键词后深入加载 |
| **触发式** | 特定场景直接读取 | 见下方触发规则 |

### 触发规则

- 写 PRD / 做交互方案 → 先读 `各角色目录/产品设计/角色说明.md`
- 分析投放/转化数据 → 先读 `各角色目录/增长策略/角色说明.md`
- 搭建 prompt / context / skill → 先读 `各角色目录/AI工程/角色说明.md`
- 做过类似的事但记不清细节 → grep `知识沉淀/` 搜关键词

## 沉淀触发

完成以下类型工作后，AI 应主动提出沉淀：
1. PRD 经历了多轮修改才达标
2. 方案被用户否定后重做（说明认知有偏差）
3. 首次跑通某个流程（MCP 接入、新工具使用）
4. 发现了反直觉的产品/业务/技术现象
5. 用户纠偏了 AI 的理解（"不是这样的，应该是……"）

详细规范见 → `沉淀规范.md`
