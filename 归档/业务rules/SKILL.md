# Context 建设与 Review

## 一、Context 分类体系

每一条输入的context，先判断属于以下哪个分类。**分类决定了review方法。**

| 分类 | 一句话定义 | 核心review手段 |
|------|-----------|---------------|
| **A. 业务框架** | 产品/渠道/角色/指标等结构性认知 | 完整性、一致性、时效性 |
| **B. 用户旅程** | 用户在产品内外的行为路径和场景 | **和线上产品对照验证** |
| **C. 数据** | 指标值、转化率、实验结论等定量信息 | 来源、口径、时效、合理性、样本量 |
| **D. 业务逻辑** | 系统实现的规则、自动化流程 | **去代码库/系统验证** |
| **E. 业务SOP** | 人执行的标准操作流程 | **和数据对照**（规定 vs 实际） |
| **F. 认知/判断** | 基于经验的判断、假设、推论 | 来源分级、标注可信度 |

### 快速分类判断

- 有数值 → **C**
- 描述"系统怎么工作" → **D**
- 描述"人怎么执行" → **E**
- 描述"用户走什么路径" → **B**
- 描述产品/渠道/角色的结构 → **A**
- "我觉得..."、"应该是..." → **F**
- 一条信息可能跨多个分类

## 二、各分类的 Review 方法

### A. 业务框架类

结构性的业务认知。相对稳定，是其他所有分析的基础前提。

| 检查项 | 做什么 |
|--------|-------|
| 完整性 | 新业务线/渠道/角色是否已覆盖 |
| 一致性 | 不同文档中同一概念的描述是否统一 |
| 时效性 | 是否反映当前业务状态而非历史 |
| 来源验证 | 框架性描述是否有事实支撑（是实际已覆盖还是规划中？） |

### B. 用户旅程类

用户在产品内外的行为路径。和渠道/场景强相关，涉及端内和端外行为。

| 检查项 | 做什么 |
|--------|-------|
| 场景对应 | 旅程是否标注了for哪个渠道/场景 |
| 端内+端外串联 | 是否只写了端内操作、遗漏了端外行为（如线下交接、电话沟通） |
| 角色切换标注 | 涉及多角色时，交接节点是否写清楚 |
| **和产品实际一致** | 旅程描述和线上产品是否一致——**用截图或实际走一遍验证**，不要凭记忆写 |
| 多路径覆盖 | 是否只写了主路径、遗漏了分叉路径 |

### C. 数据类

指标值、转化率、实验结论等定量信息。需要严格的口径和时效性。

| 检查项 | 做什么 |
|--------|-------|
| 来源 | 数据从哪来的？后台/BI/手动统计/别人给的？ |
| 口径 | 分子分母是什么？排除了什么？ |
| 时效 | 数据是最近的还是过期的？业务是否已变化？ |
| 合理性 | 数值是否在合理范围？和相关指标是否自洽？ |
| 样本量 | 样本够不够支撑结论？ |
| 精确性 | 是精确值还是估算？偏差范围？ |

**沉淀规则**：数据类context必须标注来源、时间范围、口径定义。缺任一项标记为"待校验"。

### D. 业务逻辑/流程类

系统实现的规则和自动化流程。有代码或系统配置支撑的"技术事实"。

| 检查项 | 做什么 |
|--------|-------|
| **代码库验证** | 去代码库/系统后台确认实际实现 |
| 版本确认 | 是当前线上版本还是历史版本/计划中的 |
| 系统 vs 业务含义 | 系统定义和业务团队的理解是否一致 |
| 边界条件 | 异常情况下系统怎么处理 |

**核心原则**：涉及系统实现的概念，**技术事实 > 业务习惯 > 口头约定**。当存在歧义时，以代码库为准，在文档中分开写系统定义和业务含义。

### E. 业务SOP类

人执行的标准操作流程。可能因人而异，执行偏差大。

| 检查项 | 做什么 |
|--------|-------|
| **和数据对照** | SOP说的和数据表现的是否一致 |
| 执行覆盖率 | SOP是全员执行还是部分执行 |
| 版本时效 | SOP是最新的还是过时的 |
| 一线反馈验证 | 找实际执行者确认，录音/访谈比文档更准 |
| 团队差异 | 不同团队/渠道的SOP是否相同 |

**核心原则**：SOP写的是"应该怎么做"，数据反映的是"实际怎么做"。两者不一致时，以数据为准描述现状，标注规定和实际的差异。

### F. 认知/判断类

基于经验的判断、假设、推论。不是事实，是观点。

| 检查项 | 做什么 |
|--------|-------|
| 来源分级 | 经过验证的事实 / 团队共识 / 个人判断 / 推测？ |
| 可验证性 | 这个判断能否用数据或实际观察验证？ |
| 影响程度 | 如果这个判断是错的，结论会不会变？ |
| 标注清晰 | 沉淀时是否标注了可信度等级 |

**核心原则**：认知类context可以沉淀，但**必须标注可信度等级**，不能和事实类context混写。

## 三、Context 输入与 Review 工作流

### 流程

```
输入context → 分类（A~F）→ 按分类review → 标注状态 → 沉淀到对应文件 → 更新全景表
```

### 第一步：接收输入

用户通过以下方式提供新context：
- 口述业务信息
- 粘贴文档/数据
- 分享内部链接（石墨/设计稿/看板等）
- 提供会议纪要
- 讨论中产生的新认知

**不管哪种输入方式，第一件事是分类。**

### 第二步：按分类执行Review

找到分类后，按第二章对应的Review方法逐条检查。

**Review的核心态度**：
- 不是质疑用户，是帮用户区分"我知道的"和"我觉得的"
- 该追问的必须追问，不要因为怕打断节奏就跳过
- 发现矛盾时直接指出，不要默认自己是对的

**Review提问模板**：

| 分类 | 常用追问 |
|------|---------|
| A.框架 | "这个定义是当前的还是计划调整的？" |
| B.旅程 | "这是当前线上实际流程，还是你理解的？最近有改版吗？" |
| C.数据 | "这个数据从哪拉的？时间范围和口径是什么？" |
| D.逻辑 | "这个规则在代码/系统里是怎么实现的？有没有边界情况？" |
| E.SOP | "这是文档上写的，还是一线实际在执行的？覆盖率多少？" |
| F.认知 | "这个判断有什么依据？如果错了会影响结论吗？" |

### 第三步：标注状态并沉淀

Review完成后，每条context标注：

```markdown
- **分类**：[A/B/C/D/E/F]
- **内容**：[一句话描述]
- **来源**：[数据系统 / 代码库 / 文档 / 团队共识 / 个人判断]
- **可信度**：[已验证 / 待校验 / 推测]
- **时效**：[截至YYYY-MM-DD]
- **沉淀位置**：[文件路径]
```

### 第四步：更新全景表

沉淀完成后，更新团队维护的context全景表中对应行的状态。

> 全景表是团队自己维护的持续更新文档，不在本skill中。本skill只提供分类和review方法。

## 四、交叉验证规则

不同分类的context之间需要交叉验证，防止"每条单独看都对，合在一起有矛盾"。

### 4.1 系统定义(D) × 业务含义(A/E)

当同一个概念在系统和业务中有不同含义时：
- **分开写**，不混用同一个词
- **标注优先级**：以代码库为准
- **说明差异**：解释为什么不同、各自适用场景

### 4.2 SOP(E) × 数据(C)

SOP描述"应该怎么做"，数据反映"实际怎么做"：
- 两者不一致时，以数据为准描述现状
- 覆盖率未知的SOP标注"规定如此，实际执行待确认"
- **不一致本身就是重要发现**，可能指向执行问题或SOP需要更新

### 4.3 用户旅程(B) × 产品实际(D)

旅程描述的路径要和线上产品一致：
- 用截图或实际走一遍线上流程验证
- 留意最近的改版是否影响了旅程描述
- UI元素的形态（按钮 vs 文本、弹窗 vs 浮层）要准确——这种级别的事实错误会导致方案偏差

### 4.4 多视角衔接

不同视角的context需要串联：
- 产品侧旅程(B)和执行侧SOP(E)要能对接上
- 上游策略(A)和下游数据(C)要能呼应
- 如果某个视角缺失，在全景表中标注

### 4.5 认知(F) × 事实(A/B/C/D/E)

认知判断要和其他分类的事实对照：
- 每一次对照修正都应记录，作为认知迭代的痕迹
- 高影响的认知判断（如果错了结论会变），必须主动找事实验证

## 五、常见Review失败模式

| 失败模式 | 描述 | 对策 |
|---------|------|------|
| **没看原始材料就分析** | 文档/数据拿不到，但还是给了分析意见 | 阻塞时先解决访问问题，不要凭描述做分析 |
| **把推测当事实沉淀** | 判断性信息写进文档但没标注来源 | 所有非事实类信息必须标注可信度 |
| **分析→方案跳跃** | 数据分析做完直接写方案，缺收敛的假设 | 用"我们认为X能带来Y，因为Z"格式强制收敛 |
| **单视角盲区** | 只看一侧，遗漏协作方的配合 | 方案至少从两个视角走一遍 |
| **版本断裂** | 新版文档中找不到旧版分析的引用 | 新版开头用几句话引用旧版核心逻辑 |
| **术语混用** | 同一个词在不同语境下指代不同 | 发现多义时拆开命名 |
| **修正未回溯** | 用户纠正了一个事实但没检查这个修正影响的其他结论 | 每次事实修正后，追溯所有基于旧认知的推导 |

## 六、使用场景

| 场景 | 触发方式 | 执行重点 |
|------|---------|---------|
| 新建一块业务context | "帮我把XX的背景沉淀下来" | 分类 → 逐条review → 沉淀 → 更新全景表 |
| 补充/修正已有context | "这个信息更新了/之前写错了" | 定位分类 → review新信息 → 交叉验证是否影响其他context |
| 启动分析前的context检查 | 分析前自动执行 | 扫全景表 → 确认涉及的context是否齐全 → 标注缺失项 |
| 会议纪要沉淀 | "帮我整理这次讨论" | 逐条分类 → 区分事实和判断 → 标注待确认项 |
| 周期性review | 定期主动提醒 | 扫全景表 → 检查时效性 → 标注过期context |

## 七、标注规范

对沉淀的关键信息标注来源和可信度：
- 来源明确的数据：直接引用，注明看板/时间
- 估算值：`（约X%，估算）`
- 团队共识：`（团队共识，未经数据验证）`
- 个人判断：`（基于经验判断，待验证）`
- 代码/系统确认：`（以[系统名/代码库]为准）`

---

## 能力边界

- 不替代用户做最终判断——提供review结果和建议，由用户决定
- 不直接访问数据系统——需要用户提供数据，我来校验合理性
- 不直接读代码库——需要用户确认系统实现，或通过工具辅助
- 不生成虚构context——宁可标注"未知"也不编造
