# 增长产品 PRD 规范

> 基于团队现有 [PRD 规范](https://confluence.zhenguanyu.com/pages/viewpage.action?pageId=721134945) 扩展，适用于增长方向的产品需求文档。

## 为什么需要单独的规范

增长需求通常体量小、迭代快、实验性强。现有 PRD 规范的 159 分层和完备性要求，对增长场景偏重了。

但增长需求有自己容易犯的毛病：**上来就写方案，说不清为什么有效；做完了不知道算成功还是失败；经验没沉淀，下一个需求还是拍脑袋。**

这套规范不追求面面俱到，**只抓增长需求最容易缺失的几个点**。

---

## 核心要求：五个必须说清楚的事

### 1. 问题和现状

你观察到了什么？数据是什么？

不需要长篇大论，但要有事实基础，不能只是"感觉可以做"。

### 2. 假设

**"我们认为 [做法] 能 [效果]，因为 [原因]。"**

一句话，把因果逻辑说清楚。这是增长 PRD 和普通 PRD 最大的区别——增长需求本质上都是在验证一个假设。

写假设不是为了形式，而是为了：
- 逼自己想清楚"凭什么这么做就有效"
- 事后能对着假设复盘，到底是假设对了、方案对了、还是碰巧了

**示例**：
- ✅ "我们认为，在首触电话之前通过产品端让家长提前了解到'有专属辅导老师会联系你提供服务'，能提升加微率和首通成功率，因为当前首通分析显示家长核心问题是'没有预期'——不知道会有电话，不知道老师能帮什么。"
- ✅ "通过连续完习的阶梯奖励，能提升周完习率，因为用户已有完习习惯但缺少持续动力，阶梯机制利用沉没成本让用户不愿断档。"
- ❌ "做一个激励活动提升完习率"（这是做法描述，不是假设）
- ❌ "优化预期建立流程，提升首通成功率"（没有因果推理，只有目标）

**常见问题：分析做得好但没收敛成假设。** 很多 PRD 有详细的数据分析和现状梳理，但分析完之后直接跳到了方案设计，中间缺一个"所以呢"。分析是过程，假设是结论——要把分析收敛成一句可验证的因果判断，再展开方案。

### 3. 假设支撑

假设不能是空中楼阁，需要有支撑——但不需要写论文，有就写，一两条即可：

- 之前类似活动的数据（"上次 XX 活动参与率 30%，完习率提升了 X"）
- 用户调研或反馈（"用户访谈中 X 位提到 Y"）
- 行业参照或竞品做法
- 已有的数据分析（比如"数据显示先加微后完测的用户首通率 70.6%，远高于仅加微的 67%和仅完测的 51%，说明这条路径最优"）
- 业务经验判断（坦诚标注"这是经验判断，没有硬数据"也行）

**没有任何支撑的假设 = 纯猜测**。纯猜测不是不能做，但要坦诚标注，让评审者和自己都清楚这是在赌。

**如果有多个方案在犹豫，数据可以帮你框定讨论方向。** 不要让"选方案"变成纯主观辩论。回到数据看看：每个方案本质上在验证什么假设？数据对哪个假设更有支撑？比如如果分析出的问题是"用户不知道有这个服务"（信息缺失），那"前置直接告知"就比"渐进建信任"更对症——因为问题是不知道，不是不信任。

### 4. 方案（用户视角描述）

不要上来就写功能逻辑和规则表。**先从用户视角把方案走一遍**：

> 用户在什么场景下 → 看到/遇到什么 → 做了什么 → 得到什么反馈 → 为什么这个体验能让他做出我们期望的行为

走完用户视角之后，再写功能规则、逻辑细节。这样读者先理解"这个东西怎么用、为什么有效"，再看"具体怎么实现"。

B 端需求同理，只是视角换成业务操作者：当前怎么干的 → 改成怎么干 → 为什么更好。

功能方案部分沿用团队现有 PRD 规范即可，不额外要求。

**推荐写法：当前 vs 优化后的对比。** 用几句话把改变前后的用户路径都写出来，让读者一眼看到差异。比如：

> 当前：注册 → 学习计划页（纯课程信息）→ 弱加微引导 → 突然接到陌生电话 → 懵/挂断
>
> 优化后：注册 → 学习计划页（有辅导老师信息+服务说明）→ 强化加微引导 → 完测后收到诊断报告 → 接电话时已有预期

**常见问题：如果需求涉及多个视角，每个视角都需要有用户旅程。** 比如一个需求同时涉及"产品端体验改造"和"销售端首通优化"，那产品侧的用户路径和销售侧的用户路径都要写，并且说清楚两者怎么衔接。只写了一侧的分析，另一侧直接上界面，读者就会断档。

### 5. 实验方案

做完怎么判断成败？这是增长需求最容易偷懒的地方。

必须写清楚：
- **怎么验证**：A/B 测试 / 灰度 / 前后对比
- **看什么指标**：核心看哪个指标，辅助看哪些，有没有需要保护的指标（比如防止"水完习"就要看学习时长，防止"强引导加微"就要看次留和投诉率）
- **什么算成功**：不需要精确到 5pp 这种数字——因为很多时候确实拍不准。但至少要说清楚方向和量级感（"有统计显著的正向提升"或"至少能覆盖活动成本"），以及**什么情况下算失败要止损**
- **成功了然后呢，失败了然后呢**：一句话的迭代思路

**如果有多个方案，A/B 本身就是最好的选择方式。** 与其在 PRD 里讨论半天"思路一好还是思路二好"，不如直接 A/B。两个思路往往是在验证两个不同的假设，A/B 的结果不仅能选方案，还能告诉你用户的真实心理模型是什么——这比选哪个 UI 方案更有价值。如果实在做不了 A/B，先选数据和分析更支持的那个。

## 关于定量目标

坦率说，增长需求的定量目标经常是拍的。硬要拍一个"提升 5pp"，既不准确，也容易变成事后甩锅的工具。

**推荐的做法**：
- 核心指标写**方向和量级感**（"显著提升周完习率"）而非精确数字
- 如果有历史数据参照，写参照范围（"参照上次活动，预期提升 2-5pp"）
- 过程指标和防护指标比核心目标值更重要——它们帮你理解"为什么有效/无效"
- 把精力花在**实验设计和数据拆解**上，而不是花在拍一个经不起推敲的目标数字上

## 关于文档结构

不要求严格的 1-5-9 分稿，但建议用标题层级或页面分区做自然分层，让不同读者快速定位：

- **开头**（框架）：问题、假设、实验方案 → 快速理解"为什么做、怎么验证"
- **中间**（方案）：用户视角描述 + 功能逻辑 → 理解"怎么做"
- **末尾**（细节）：规则明细、埋点、文案、技术依赖 → 开发交付用

一个小需求，框架部分可能就 3-5 句话，方案部分一页，细节部分看复杂度。**不要求篇幅，要求该说的说到位。**

如果文档用了 Motiff 的多页结构（比如 1-1 放分析，5-2 放方案），方案页的开头最好用几句话把分析页的结论带过来——不是复制一遍，而是一段话的上下文引用。因为看方案的人（技术、设计）不一定会仔细看分析页，他们需要在方案页就能理解"为什么这么做"。

## 实验结论（上线后回填）

在 PRD 末尾留一个区域，活动/实验结束后回来填：

- 假设成立吗？
- 关键发现是什么？
- 下一步做什么？

这不是形式主义。增长团队最大的资产是**"试过什么、学到什么"**，不沉淀就白做了。

---

## 速查

写增长 PRD 时，对照这五条自检：

1. **问题**：我要解决什么问题？数据现状是什么？
2. **假设**：我认为 [做法] 能 [效果]，因为 [原因]——分析做完了，有没有收敛成一句因果判断？
3. **假设支撑**：有什么依据支撑这个假设？如果有多个方案，数据更支持哪个？
4. **方案**：从用户视角走一遍——用户怎么用、为什么有效？当前路径 vs 优化后路径的差异写清楚了吗？
5. **实验**：怎么验证、看什么指标、成功/失败后怎么办？多个方案能不能直接 A/B？
