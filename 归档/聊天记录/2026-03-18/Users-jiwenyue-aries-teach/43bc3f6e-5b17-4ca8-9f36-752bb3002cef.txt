> 本示例记录一篇 PRD 在 review 中暴露的典型问题，用于说明 prd-writer 各章节标准的实际意义。
> 原文档：https://confluence.zhenguanyu.com/pages/viewpage.action?pageId=1039568861

## 文档概况

| 项目 | 内容 |
|------|------|
| 需求名称 | 完习激励抽奖活动 |
| 核心目标 | 提升 W13+ 用户单周全环节完习率 5pp |
| 方案 | 连续完习 1-4 周获得阶梯奖励（抽奖券+海豚币） |
| Review 结论 | ⚠️ 建议先补充问题分析和用户视角，再进入评审 |

## Review 发现的问题

### 问题 1：缺少用户视角（对应模板 1.2）

**原文写法**：
> 从"助理侧的促完习活动"角度切入，直接进入活动方案。

**问题**：
只从业务运营角度出发，没有回答最根本的问题——W13+ 的用户为什么不完习了？

**Review 指出**：
到习完习率高达 90%+，说明来上课的用户基本都能完成，真正的缺口在"不来上课"。那为什么不来？是学习动力在 M3 后自然衰减？是课程吸引力下降？还是生活中有更优先的事？

**应该怎么写**：
> 用户不完习的原因是 XX → 我们认为在现阶段，用外部激励能在一定程度上应对 → 所以选择抽奖+海豚币的方式

---

### 问题 2：问题归因链断裂（对应模板 1.3）

**原文写法**：
> - "单周全环节完习率有提升空间"——现象
> - "需要周维度抓手"——已经是方案方向
> - "通过阶梯激励增强连续完习的留存动机"——解决方案

**问题**：
从「现象」直接跳到了「方案」，中间少了最关键的一环——为什么会这样？原因是什么？

**应该怎么写**：
现象（完习率 55%-60%）→ 数据追问（到习完习 90%+ 说明问题在不到习）→ 原因分析（M3 衰减、新鲜感消退等）→ 解法方向

---

### 问题 3：数据有了但分析不够深（对应模板 1.3）

**原文数据**：
> 全完习 55%-60%、到习完习 90%+、M3 衰减最快、寒暑假上抬

**问题**：
这些数据背后的线索没有被追问：
- 到习完习 90%+ → 问题主要出在"不到习"，那"不到习"的原因是什么？
- M3 衰减最快 → 第三个月发生了什么？新鲜感消退？课程阶段切换？
- 寒暑假上抬 → 是时间更充裕，还是家长监督更强？

---

### 问题 4：目标缺依据（对应模板 2.3）

**原文写法**：
> 各周期全环节完习提升 5pp

**问题**：
- 5pp 的依据是什么？基于以往类似活动的数据？还是业务期望？
- 活动只有 4 周，结束后会怎样？如果完习率回落，这 4 周的提升带来的实际业务价值是什么？
- 海豚币和奖品的预算大概是多少？5pp 完习率提升对应多少留存改善？大致 ROI 合不合理？

---

### 问题 5：缺少方案定位（对应模板 4.1）

**问题**：
抽奖活动本质上是外部激励手段，文档没有正视其局限性：
- 活动结束后，用户的完习行为会不会回落？
- 长期来看，外部激励是否足够？根本性的留存要靠内容和体验

**应该怎么写**：
> "这是一个短期运营活动，目标是在 3-4 月期间提振完习率。长期的完习策略还需要从内容/产品体验侧去解决，但短期先用这个活动顶一下。"

---

### 问题 6：缺少方案对比（对应模板 4.2）

**问题**：
提升完习率的路线有很多——内容优化、助理跟进策略调整、社交激励（学习小组/排行榜）、产品机制（streak/成就系统）等。文档只提了"抽奖+海豚币"一条路，没有说明为什么选这个。

---

### 问题 7：缺少归因设计（对应模板 6.3）

**原文**：
只列了活动过程指标（参加人数、获奖人数、抽奖人数），缺少效果评估设计：
- 怎么区分"因为活动多完习了"和"本来就会完习"的用户？
- 活动结束后 1-2 周的完习率变化很重要——如果马上回落，说明活动只是"借了未来的完习"
- "10 分钟完习率、单科全完习率"和活动效果的关系是什么

---

### 问题 8：关键定义和规则设计缺依据

- "周全环节完习"定义为"任一科目当周必学内容完习"，标准是否太低？三科用户只完成一个科目就算？
- 奖励阶梯 1/1/2/2 张抽奖券、0/200/0/500 海豚币的设计依据是什么？
- 如果效果好，后续打算怎么办？常态化还是不定期做？

---

# PRD Review

产品 Leader 视角的 PRD 评审工具。v1 审问题分析与方案方向，v5 审交互设计。

## 工作流

### Step 1：获取 PRD 内容

**Confluence 文档**（v1/v5 均适用）：

```
MCP server: user-shimo
Tool: get_confluence_content
Arguments: { "page": "<url>", "pageId": "<id>" }
```

**Motiff 设计稿**（v5 交互稿）：

从 Motiff URL `https://motiff.com/file/{docId}?nodeId={nodeId}` 中提取参数。nodeId 中的 `%3A` 需解码为 `:`。

```
MCP server: user-motiff
Tool: get_motiff_node_screenshot  # 获取设计截图
Arguments: { "docId": "<docId>", "nodeId": "<nodeId>" }

Tool: get_motiff_node             # 获取 HTML 结构（辅助分析布局和组件）
Arguments: { "docId": "<docId>", "nodeId": "<nodeId>" }
```

用户可能同时提供 Confluence 链接和 Motiff 链接，都需要拉取。

### Step 2：识别版本

从 PRD 标题中的版本号判断：
- 标题格式：`产品名X.X-{159版本}-{副版本}`，如 `通用题库 CMS1.0-1-3` 中 `-1-` 表示 v1
- 版本 1 = v1 概念稿，5 = v5 主功能稿，9 = v9 细节稿
- 无法判断时问用户
- v9 不在 review 范围内，如果是 v9 告知用户

### Step 3：评估 Review 深度

**深度 review**（每个维度详细分析，给具体建议）— 满足任一条件：
- 影响核心业务指标：首单 ROI、UE、体验课转化率、在课留存（周完习率）、长续率、退费率
- 影响全量用户（而非小部分用户）
- 涉及多个部门协作
- 改动范围大（多个模块/页面）
- 开发难度高

**标准 review**（标注有问题的维度，给要点）：不满足上述条件。

无法判断时问用户："这个需求的影响面和复杂度大概是什么水平？"

### Step 4：按版本 Review

详细检查标准见 [review-checklist.md](review-checklist.md)。

#### v1 Review：问题分析与方案方向

核心判断：**问题值得做吗？方向对吗？**

| # | 维度 | 核心问题 |
|---|------|---------|
| 1 | **用户视角** | 这个需求是从用户需求出发的吗？对用户的影响说清楚了吗？ |
| 2 | 问题定义 | 要解决什么问题，说清楚了吗？ |
| 3 | 问题分析 | 做了严肃分析吗？需求来源、根因挖掘 |
| 4 | 收益判断 | 收益清晰吗？长短期、重要紧急 |
| 5 | 是否直击根本 | 方案是否简单直接解决根本问题 |
| 6 | 竞品/行业参照 | 别人怎么做的、为什么我们这样做 |
| 7 | 方案路线对比 | 想过其他路线吗？为什么选当前方案 |
| 8 | 效果评估思路 | 做完怎么知道成功了 |
| 9 | 待决策点 | 还有哪些模糊需要决策的问题 |

**关于「用户视角」**：这不只是一个维度，而是贯穿 review 的底层检查。几乎所有需求都应该回归到用户需求——即使是业务提出的需求，业务指标的变化本质上是对用户需求的回应。需要说清楚对用户的影响是什么、能不能带来显著的体验变化、进而如何影响业务。极少数纯算账/经营模式类需求可以豁免。

**门禁判断：**
- ✅ 可以推进到 v5
- ⚠️ 需要在特定点上补充后重新 review
- ❌ 方向有问题，建议重新分析

#### v5 Review：交互设计

前提：v1 方向已过。核心判断：**交互走得通吗？设计合理吗？**

| # | 维度 | 核心问题 |
|---|------|---------|
| 1 | 场景还原 | 主流程走得通吗？（谁→页面→看到什么→想做什么→怎么操作） |
| 2 | 交互逻辑自洽 | 各功能点正常逻辑是否清晰、自洽 |
| 3 | 与 v1 方向一致 | 交互方案是否忠实于 v1 定的方向 |
| 4 | 设计一致性 | 是否复用已有组件和交互模式，避免不必要的新发明 |

### 1. 用户视角（贯穿性底层检查）

**要回答的问题：** 这个需求是从用户需求出发的吗？对用户的影响说清楚了吗？

**核心理念：** 业务指标的变化大多数是对用户需求的回应。即使是业务方提出的需求，也应该回归到用户需求中去——用户遇到了什么问题、用户会怎么感受、对用户的体验改变是什么、这个体验改变如何传导到业务指标。

**检查标准：**
- PRD 的叙事起点是"用户遇到了什么问题"，而非"业务要做什么功能"
- 清楚描述了对用户的影响是什么——不是抽象的"提升体验"，而是具体的用户场景和感受变化
- 能回答"这个改动对用户来说，体验会有显著变化吗？"
- 如果涉及业务指标（转化率、留存等），说清楚了指标变化和用户体验变化之间的因果链
- 方案选择的理由能回到用户场景，而非只是"竞品这么做""老板要求"

**常见问题：**
- 全程从功能/业务/技术视角描述，用户只是一个抽象概念
- 业务提了一个需求，PM 直接接了就做，没有追问"这背后用户的需求到底是什么"
- 说了"提升用户体验"但说不出具体是什么体验、怎么提升、用户能感知到吗
- 方案对用户的实际影响很小，但被包装成很重要的需求
- 混淆"我们想让用户做的事"和"用户自己想做的事"

**追问方向：**
- "这个需求解决的是用户的什么问题？用户自己知道自己有这个问题吗？"
- "做完之后，用户的使用体验会有什么具体变化？变化大吗？"
- "你说的这个业务指标变化，对应的是用户行为的什么改变？"

**豁免情况：** 纯算账/经营模式类需求（如定价策略调整、SKU 结构变更等）可能不需要强制回到用户视角，但这类需求非常少。如果 PM 说"这个不涉及用户"，追问确认是否真的不涉及。

### 2. 问题定义

**要回答的问题：** 要解决什么问题，说清楚了吗？

**检查标准：**
- 用"问题/痛点"而非"功能"来描述需求
- 能回答"不做这个，用户/业务会怎样？"
- 问题描述是事实性的，有数据或实例支撑

**常见问题：**
- 把解法当问题写（"我们需要做一个 XX 功能" ← 这不是问题定义）
- 问题描述太笼统（"用户体验不好"）

**好的标准（示范）：**

### 3. 问题分析

**要回答的问题：** 做了严肃分析吗？

**检查标准：**
- 需求来源清晰：是数据发现、业务方反馈、用户投诉、还是战略判断？

- 分析有依据，不是纯主观推测

**常见问题：**
- 只描述现象不挖原因
- 用个例代替系统分析（"有个用户反馈说…"就定性了整个问题）
- 需求来源不明（不知道这个需求从哪冒出来的）
- 分析链断裂（从现象直接跳到方案，中间的推理过程缺失）

**追问方向：**
- "这个数据/现象的背后原因是什么？你怎么确认的？"
- "除了这个原因，还有没有其他可能性？"
- "这个判断有数据支撑吗？还是假设？"

### 4. 收益判断

**要回答的问题：** 解决后的收益清晰吗？

**检查标准：**

- 区分了短期收益和长期收益
- 在重要-紧急矩阵中的位置清晰
- 收益和核心业务指标有关联（首单 ROI、UE、体验课转化率、在课留存、退费率）

**常见问题：**
- 收益描述模糊（"提升用户体验""提高效率"）
- 只讲短期止血，不讲长期价值（或反过来）
- 收益和问题对不上（解决的是 A 问题，讲的收益是 B 方向的）
- 没有量级感知（不知道影响多少用户、影响多大比例）

### 5. 是否直击根本

**要回答的问题：** 方案是否简单直接解决根本问题？

**检查标准：**

**常见问题：**

**检查标准：**

- 我们方案和竞品差异的原因清晰

**常见问题：**

- 竞品分析浮于表面（只截了图，没分析背后的设计逻辑）

**常见问题：**

**检查标准：**

**常见问题：**

- **评价**：PRD 的叙事起点是"助理侧的促完习活动"，全程从业务运营角度切入。但你自己的数据里藏着一个关键信息——到习完习率高达 90%+，说明**来上课的用户基本都能完成，真正的缺口在"不来上课"**。这是一个非常有价值的发现，但文档没有从用户角度追问下去：他们为什么不来？是 M3 后学习动力自然衰减？课程吸引力下降？还是生活里有了更优先的事？
- **建议**：在背景部分加一段用户视角的分析。最直接的做法是**跟助理聊一下**，W13+ 不完习的用户通常是什么情况——助理对这些用户的感知可能比数据更直接。然后把思考链写出来：

  > 用户不完习的主要原因是 XX → 我们认为在现阶段，用外部激励能在一定程度上拉回这部分用户 → 所以选择抽奖+海豚币的方式

### 2. 问题定义
- **判断**：❌
- **评价**：背景里的三句话分别是：
  - "单周全环节完习率有提升空间"——**现象**
  - "需要周维度抓手"——已经是**方案方向**了
  - "通过阶梯激励增强连续完习的留存动机"——这是**解决方案**本身

  从"现象"直接跳到了"方案"，中间最关键的一环——**为什么完习率不高？原因是什么？**——被跳过了。这属于典型的"把解法当问题写"。
- **建议**：把背景拆成两段——先把**问题**讲完（现象+原因），再讲你打算**怎么解决**。可以参考这个结构：
  - 现象：全完习率 55%-60%，M3 衰减最快
  - 原因分析：到习完习 90%+ 说明问题出在"不到习"，不到习的可能原因是...
  - 切入方向：在当前阶段，选择用外部激励来提振到习率

### 3. 问题分析
- **判断**：❌
- **评价**：你放了很好的数据基础（55%-60%、90%+、M3 衰减、寒暑假上抬），这是好的。但这些数据里的线索没有被追问：
  - 到习完习 90%+ → 问题主要出在"不到习"，那**不到习的原因**是什么？
  - M3 衰减最快 → **第三个月发生了什么？** 新鲜感消退？课程阶段切换？
  - 寒暑假上抬 → 是因为时间充裕，还是家长在家监督更强？

  分析链在"数据描述"这一步就断了，没有往下挖 why。
- **建议**：不需要做特别重的分析，哪怕追问一两层 why 就够了。比如可以分年级/科目看看衰减模式有没有差异，或者看看 M3 衰减的用户画像跟其他月份有什么不同。

### 4. 收益判断
- **判断**：⚠️
- **评价**："各周期全环节完习提升5pp"——有具体数字，但三个关键问题没回答：
  1. **5pp 的依据是什么？** 基于以往类似活动的数据？还是业务期望？
  2. **活动只有 4 周，结束后会怎样？** 如果完习率回落，这 4 周的提升带来的实际业务价值是什么？
  3. **成本收益关系**：海豚币和奖品的预算大概是多少？5pp 提升对应多少留存改善？ROI 合理吗？

  只有"做到多少"没有"为什么是这个数"，收益判断缺乏说服力。
- **建议**：补充目标依据（哪怕是"参考XX活动的数据"或"业务期望值，后续根据数据调整"），再粗略估一下成本。

### 5. 是否直击根本
- **判断**：⚠️
- **评价**：如果根因是"用户不到习"，那抽奖激励本质上是用外部激励把人"拉回来"——这不是在解决根因（为什么不到习），而是在绕过根因。这不一定是错的——可能短期内确实没有更好的办法——但文档需要正视这一点。
- **建议**：在方案部分坦诚说明：

  > "这是一个短期运营活动，目标是在 3-4 月期间提振完习率。长期的完习策略还需要从内容/产品体验侧去解决，但短期先用这个活动顶一下。"

  讲清楚了，大家对这件事的预期就对齐了。

### 6. 竞品/行业参照
- **判断**：❌
- **评价**：文档中没有任何竞品或行业参照。"连续学习激励"在教育行业里是一个非常成熟的设计方向——Duolingo 的 streak 机制、其他教育 App 的打卡奖励、学习社群的排行榜等——这些已有大量实践和效果数据。完全不参考就直接做，容易错过已被验证的有效设计。
- **建议**：不需要做很重的竞品分析，快速看 2-3 个行业案例（Duolingo streak、其他 K12 App 的打卡奖励），总结它们的做法和效果，给你的方案找支撑或启发。

### 7. 方案路线对比
- **判断**：❌
- **评价**：只提了"抽奖+海豚币"一条路线。但提升完习率的路线其实有不少：内容优化（让课更吸引人）、助理跟进策略调整（更精准的催课）、社交激励（学习小组/排行榜）、产品机制（streak/成就系统）、外部物质激励（抽奖/补贴）等。不知道你考虑过其他方向没有。
- **建议**：补一段简要的方案对比，不需要每个都详细分析，说清楚"我考虑过 A/B/C，当前阶段选 D 的理由是..."就够了。

### 8. 效果评估思路
- **判断**：⚠️
- **评价**：列了活动过程指标（参加人数、获奖人数、抽奖人数）和结果指标（10 分钟完习率、单科全完习率），基本面有了。但缺三个关键设计：
  1. **归因**：怎么区分"因为活动多完习了"和"本来就会完习"的用户？有没有可能设一个对照组？
  2. **活动后观察期**：活动结束后 1-2 周的完习率变化很重要——如果马上回落，说明活动只是"借了未来的完习"
  3. **指标关系**："10 分钟完习率、单科全完习率"和活动效果是什么关系？没有说明
- **建议**：补充归因思路（哪怕是"通过对比活动参与者 vs 未参与者的完习率变化"），加上活动后 1-2 周的观察期设计。

### 9. 待决策点
- **判断**：⚠️
- **评价**：文档里有几个隐含的模糊地带没有暴露：
  1. **"周全环节完习"的标准**：定义是"任一科目当周必学内容完习"就算。一个三科用户只完成一个科目就算"全环节完习"？这个标准会不会太低？
  2. **奖励阶梯的依据**：1/1/2/2 张抽奖券、0/200/0/500 海豚币——这个设计有什么依据？如果是先试试的，可以标注"初始方案，根据数据迭代"
  3. **活动延续性**：如果效果好，后续打算怎么办？常态化做还是不定期做？
  4. **技术可行性**：文档写了"需要调研现在的抽奖活动是否支持直接接口下发"——这个还没确认，是阻塞项吗？

## PRD 类型判断

PRD 主要分为两种类型，撰写侧重点不同。**动笔前先判断类型**。

### 快速验证型

**特征**：短期活动、低成本实验、运营抓手、快速试错
**典型案例**：完习激励抽奖活动、限时促销、A/B 测试型需求
**核心要回答的问题**：

| # | 问题 | 说明 |
|---|------|------|
| 1 | **为什么有效？** | 方案的有效性论证——基于什么逻辑/数据认为这个方案能起作用 |
| 2 | **成本是否可控？** | 开发成本、运营成本、奖品预算等是否在合理范围 |
| 3 | **有没有副作用？** | 是否会带来额外损害——如功能误用导致用户认知模糊、破坏现有体验、挤占其他资源等 |

**撰写原则**：
- 不需要做很深的用户调研和根因分析——快速验证的价值在于"试了才知道"
- 重点在方案的**有效性论证**、**成本可控**、**风险可控**
- 问题分析点到即可，但要诚实——知道什么、不知道什么、这次试验想验证什么
- 方案定位要清晰：这是一个短期实验，不是长期机制

### 完整方案型

**特征**：产品功能新增/重构、影响面大、开发成本高、长期影响
**典型案例**：断课老用户增加前测、新功能上线、流程重设计
**核心要回答的问题**：

| # | 问题 | 说明 |
|---|------|------|
| 1 | **为什么要做？** | 用户视角的问题分析、完整的归因链 |
| 2 | **为什么这么做？** | 方案对比、竞品参照、设计依据 |
| 3 | **做了会怎样？** | 收益测算、ROI、长期影响 |

**撰写原则**：
- 需要完整的用户视角和问题归因
- 方案对比和竞品分析要认真做
- 目标测算要有依据、成本收益要算清楚

### 如何判断类型？

| 维度 | 快速验证型 | 完整方案型 |
|------|-----------|-----------|
| 开发周期 | ≤1 周 或 纯配置 | >1 周 |
| 影响范围 | 可控/可回滚/有时限 | 长期生效/不可逆 |
| 失败成本 | 低（试错代价小） | 高（浪费资源/影响体验） |
| 方案性质 | 运营活动/实验/临时策略 | 产品功能/流程/机制 |

如果拿不准，按**完整方案型**处理更安全。

  contents: # 增长产品 PRD 规范

> 基于团队现有 [PRD 规范](https://confluence.zhenguanyu.com/pages/viewpage.action?pageId=721134945) 扩展，适用于增长方向的产品需求文档。

## 为什么需要单独的规范

增长需求通常体量小、迭代快、实验性强。现有 PRD 规范的 159 分层和完备性要求，对增长场景偏重了。

但增长需求有自己容易犯的毛病：**上来就写方案，说不清为什么有效；做完了不知道算成功还是失败；经验没沉淀，下一个需求还是拍脑袋。**

这套规范不追求面面俱到，**只抓增长需求最容易缺失的几个点**。

---

## 核心要求：五个必须说清楚的事

### 1. 问题和现状

你观察到了什么？数据是什么？

不需要长篇大论，但要有事实基础，不能只是"感觉可以做"。

### 2. 假设

**"我们认为 [做法] 能 [效果]，因为 [原因]。"**

一句话，把因果逻辑说清楚。这是增长 PRD 和普通 PRD 最大的区别——增长需求本质上都是在验证一个假设。

写假设不是为了形式，而是为了：
- 逼自己想清楚"凭什么这么做就有效"
- 事后能对着假设复盘，到底是假设对了、方案对了、还是碰巧了

**示例**：
- ✅ "我们认为，在首触电话之前通过产品端让家长提前了解到'有专属辅导老师会联系你提供服务'，能提升加微率和首通成功率，因为当前首通分析显示家长核心问题是'没有预期'——不知道会有电话，不知道老师能帮什么。"
- ✅ "通过连续完习的阶梯奖励，能提升周完习率，因为用户已有完习习惯但缺少持续动力，阶梯机制利用沉没成本让用户不愿断档。"
- ❌ "做一个激励活动提升完习率"（这是做法描述，不是假设）
- ❌ "优化预期建立流程，提升首通成功率"（没有因果推理，只有目标）

**常见问题：分析做得好但没收敛成假设。** 很多 PRD 有详细的数据分析和现状梳理，但分析完之后直接跳到了方案设计，中间缺一个"所以呢"。分析是过程，假设是结论——要把分析收敛成一句可验证的因果判断，再展开方案。

### 3. 假设支撑

假设不能是空中楼阁，需要有支撑——但不需要写论文，有就写，一两条即可：

- 之前类似活动的数据（"上次 XX 活动参与率 30%，完习率提升了 X"）
- 用户调研或反馈（"用户访谈中 X 位提到 Y"）
- 行业参照或竞品做法
- 已有的数据分析（比如"数据显示先加微后完测的用户首通率 70.6%，远高于仅加微的 67%和仅完测的 51%，说明这条路径最优"）
- 业务经验判断（坦诚标注"这是经验判断，没有硬数据"也行）

**没有任何支撑的假设 = 纯猜测**。纯猜测不是不能做，但要坦诚标注，让评审者和自己都清楚这是在赌。

**如果有多个方案在犹豫，数据可以帮你框定讨论方向。** 不要让"选方案"变成纯主观辩论。回到数据看看：每个方案本质上在验证什么假设？数据对哪个假设更有支撑？比如如果分析出的问题是"用户不知道有这个服务"（信息缺失），那"前置直接告知"就比"渐进建信任"更对症——因为问题是不知道，不是不信任。

### 4. 方案（用户视角描述）

不要上来就写功能逻辑和规则表。**先从用户视角把方案走一遍**：

> 用户在什么场景下 → 看到/遇到什么 → 做了什么 → 得到什么反馈 → 为什么这个体验能让他做出我们期望的行为

走完用户视角之后，再写功能规则、逻辑细节。这样读者先理解"这个东西怎么用、为什么有效"，再看"具体怎么实现"。

B 端需求同理，只是视角换成业务操作者：当前怎么干的 → 改成怎么干 → 为什么更好。

功能方案部分沿用团队现有 PRD 规范即可，不额外要求。

**推荐写法：当前 vs 优化后的对比。** 用几句话把改变前后的用户路径都写出来，让读者一眼看到差异。比如：

> 当前：注册 → 学习计划页（纯课程信息）→ 弱加微引导 → 突然接到陌生电话 → 懵/挂断
>
> 优化后：注册 → 学习计划页（有辅导老师信息+服务说明）→ 强化加微引导 → 完测后收到诊断报告 → 接电话时已有预期

**常见问题：如果需求涉及多个视角，每个视角都需要有用户旅程。** 比如一个需求同时涉及"产品端体验改造"和"销售端首通优化"，那产品侧的用户路径和销售侧的用户路径都要写，并且说清楚两者怎么衔接。只写了一侧的分析，另一侧直接上界面，读者就会断档。

### 5. 实验方案

做完怎么判断成败？这是增长需求最容易偷懒的地方。

必须写清楚：
- **怎么验证**：A/B 测试 / 灰度 / 前后对比
- **看什么指标**：核心看哪个指标，辅助看哪些，有没有需要保护的指标（比如防止"水完习"就要看学习时长，防止"强引导加微"就要看次留和投诉率）
- **什么算成功**：不需要精确到 5pp 这种数字——因为很多时候确实拍不准。但至少要说清楚方向和量级感（"有统计显著的正向提升"或"至少能覆盖活动成本"），以及**什么情况下算失败要止损**
- **成功了然后呢，失败了然后呢**：一句话的迭代思路

**如果有多个方案，A/B 本身就是最好的选择方式。** 与其在 PRD 里讨论半天"思路一好还是思路二好"，不如直接 A/B。两个思路往往是在验证两个不同的假设，A/B 的结果不仅能选方案，还能告诉你用户的真实心理模型是什么——这比选哪个 UI 方案更有价值。如果实在做不了 A/B，先选数据和分析更支持的那个。

---

## 关于定量目标

坦率说，增长需求的定量目标经常是拍的。硬要拍一个"提升 5pp"，既不准确，也容易变成事后甩锅的工具。

**推荐的做法**：
- 核心指标写**方向和量级感**（"显著提升周完习率"）而非精确数字
- 如果有历史数据参照，写参照范围（"参照上次活动，预期提升 2-5pp"）
- 过程指标和防护指标比核心目标值更重要——它们帮你理解"为什么有效/无效"
- 把精力花在**实验设计和数据拆解**上，而不是花在拍一个经不起推敲的目标数字上

---

## 关于文档结构

不要求严格的 1-5-9 分稿，但建议用标题层级或页面分区做自然分层，让不同读者快速定位：

- **开头**（框架）：问题、假设、实验方案 → 快速理解"为什么做、怎么验证"
- **中间**（方案）：用户视角描述 + 功能逻辑 → 理解"怎么做"
- **末尾**（细节）：规则明细、埋点、文案、技术依赖 → 开发交付用

一个小需求，框架部分可能就 3-5 句话，方案部分一页，细节部分看复杂度。**不要求篇幅，要求该说的说到位。**

如果文档用了 Motiff 的多页结构（比如 1-1 放分析，5-2 放方案），方案页的开头最好用几句话把分析页的结论带过来——不是复制一遍，而是一段话的上下文引用。因为看方案的人（技术、设计）不一定会仔细看分析页，他们需要在方案页就能理解"为什么这么做"。

---

## 实验结论（上线后回填）

在 PRD 末尾留一个区域，活动/实验结束后回来填：

- 假设成立吗？
- 关键发现是什么？
- 下一步做什么？

这不是形式主义。增长团队最大的资产是**"试过什么、学到什么"**，不沉淀就白做了。

## 速查

写增长 PRD 时，对照这五条自检：

1. **问题**：我要解决什么问题？数据现状是什么？
2. **假设**：我认为 [做法] 能 [效果]，因为 [原因]——分析做完了，有没有收敛成一句因果判断？
3. **假设支撑**：有什么依据支撑这个假设？如果有多个方案，数据更支持哪个？
4. **方案**：从用户视角走一遍——用户怎么用、为什么有效？当前路径 vs 优化后路径的差异写清楚了吗？
5. **实验**：怎么验证、看什么指标、成功/失败后怎么办？多个方案能不能直接 A/B？
